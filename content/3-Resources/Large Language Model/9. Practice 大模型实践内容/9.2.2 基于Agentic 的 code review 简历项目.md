# 系统架构全景

先从整体看这个系统的分层设计。整个 Code Review Agent 分三层，每层职责完全独立，互不耦合：

* 技能层：用 markdown 写的 SKILL.md 文件，定义 LLM 在每个阶段应该做什么、遵循什么规则、输出什么格式。技能层不包含任何 Python 代码，纯粹是 prompt 工程的产物。
* Agent 层：实现 Claude 风格的 tool-use 主循环，负责调用 LLM、解析响应、分发工具调用、管理 messages 列表。Agent 层不关心具体工具的实现，也不关心技能文件的内容。
* 工具层：只管「怎么执行」——每个工具函数封装一个具体的 API 调用，接受结构化参数，返回结构化结果。工具层不知道自己是在哪个 review 阶段被调用的。

这种三层分离带来的最大好处是：可以独立修改任何一层而不影响其他层。比如我想改 triage 的判断规则，只需要编辑 SKILL.md，不需要碰任何 Python 代码；想增加一个新工具，只需要在 tools/ 里加函数并在 tool\_router 里注册，不需要改 Agent 主循环；想换一个 LLM，只需要改 llm\_client.py 里的 API 调用，技能文件和工具都不需要动。

# Agent 主循环深度解析

runner.py 是整个系统的核心。理解这个文件，就理解了 AI Agent 的运作原理。

## 主循环的基本结构

每次 review 从 run() 方法开始，进入一个 while 循环，每次循环称为一轮：

```python
def run(self, pr_url: str) -> AgentResult:
    # 1. 初始化 messages（system prompt 已在 __init__ 里通过 load_combined 加载）
    messages = [{"role": "user", "content": f"请对这个 PR 进行 code review: {pr_url}"}]

    for iteration in range(self.max_iterations):  # max_iterations = 30
        # 2. 调用 LLM，获取响应
        response = self.llm_client.create(messages=messages)

        # 3. 解析响应，提取 tool_use 块
        tool_use_blocks = [b for b in response.content if b.type == "tool_use"]

        # 4. 如果没有 tool_use，说明 LLM 认为 review 完成了
        if response.stop_reason == "end_turn" or not tool_use_blocks:
            break

        # 5. 执行所有 tool_use，收集 tool_results
        tool_results = []
        for tool_use in tool_use_blocks:
            result = self.tool_router.execute(tool_use.name, tool_use.input)
            tool_results.append({
                "type": "tool_result",
                "tool_use_id": tool_use.id,
                "content": [{"type": "text", "text": json.dumps(result)}]
            })

        # 6. 把 assistant 响应和 tool_results 追加到 messages，继续下一轮
        messages.append({"role": "assistant", "content": response.content})
        messages.append({"role": "user", "content": tool_results})

    return AgentResult(...)
```

## 轮数设定

30 轮是安全上限，不是预期的正常轮数。一次完整的 review 正常需要多少轮？

* Phase 1（Triage）：1-2 轮。调用 get\_pull\_request 获取 PR 信息，判断是否适合自动 review。
* Phase 2（Analyze）：2-4 轮。调用 get\_pull\_request\_files、list\_commits、memory\_get\_all 采集数据。
* Phase 3（Review）：1 轮。LLM 基于采集的数据做分析，输出 issues JSON。这轮通常不调用工具，LLM 直接在 text 里输出分析结果。
* Phase 4（Act）：3-6 轮。提交 review comments、创建 Fix PR（需要多次 GitHub API 调用）、更新 Memory。

所以正常情况下 8-15 轮就够了。30 轮的上限是为了防止 LLM 陷入异常循环——比如某个工具一直返回 error，LLM 不断重试，或者 LLM 误判还没完成而继续调用工具。超过 30 轮强制停止，session\_end 记录 iterations=30 作为异常标记，这类轨迹在导出训练数据时会被过滤掉。

## stop\_reason 的处理逻辑

Claude API 的响应有几种 stop\_reason，每种含义不同：

* end\_turn：LLM 认为任务完成，没有更多工具需要调用。这是正常结束的信号。
* tool\_use：LLM 想调用工具，需要执行工具并把结果返回给 LLM。这是继续循环的信号。
* max\_tokens：LLM 的输出被截断（超出 max\_tokens 限制）。这通常意味着 LLM 的分析结果不完整，需要增大 max\_tokens 或压缩 context。
* stop\_sequence：触发了自定义停止序列。这个项目没有用自定义停止序列。

主循环只在 stop\_reason == end\_turn 或没有 tool\_use blocks 时退出。其他情况都继续循环，直到达到 30 轮上限。

## extended thinking 的处理

Claude claude-opus-4-6 支持 extended thinking，在生成最终回复之前先进行长链推理。thinking 内容以 thinking block 的形式出现在 response.content 里：

```python
# response.content 可能包含三种 block：
[
    {"type": "thinking", "thinking": "先分析这个 PR 的改动范围..."},  # 推理过程
    {"type": "text", "text": "我来分析这个 PR..."},                    # 文字说明
    {"type": "tool_use", "id": "tool_001", "name": "get_pull_request", "input": {...}}  # 工具调用
]

# 主循环把整个 response.content 追加到 messages（包括 thinking block）
# 这样下一轮 LLM 能看到自己之前的推理过程，保持思路连贯
```

thinking block 在 SFT 数据导出时需要特殊处理：保留在 content 字段里，但不放进 tool\_calls 字段，这样不影响工具调用格式的学习。

# 技能系统与 load\_combined() 深度解析

技能系统是这个项目 Prompt 工程的核心，也是 Bug 1 和 Bug 4 的所在地。

## 为什么要拆分子技能？

最初的设计是把所有规则放在一个 SKILL.md 里。这个方案有几个问题：

* 文件太长，难以维护。triage 规则、token budget 策略、review checklist、fix-PR 模板放在一起，改一处容易影响另一处。
* LLM 注意力分散。在 triage 阶段，LLM 不需要知道 fix-PR 的格式规范；在 act 阶段，LLM 不需要知道 token budget 策略。把所有内容放在一起，LLM 需要从长 prompt 里自己找相关内容。
* 协作困难。如果多人维护这个系统，每个人只负责一个子技能，改各自的文件，不会互相冲突。

拆分成 5 个子技能后，每个文件职责单一，长度可控（200-500 行），修改和调试都更方便。

## load\_combined() 的实现与 Bug 4 修复

load\_combined() 的作用是把多个子技能的 SKILL.md 合并成一个完整的 system prompt。实现看起来很简单，但有个关键细节：

```python
# skill_loader.py 核心逻辑

def load_skill(self, skill_name: str, include_references: bool = True) -> str:
    skill_dir = self.skills_dir / skill_name
    skill_file = skill_dir / "SKILL.md"
    content = skill_file.read_text()

    # 剥离 YAML frontmatter（--- 开头的元数据块）
    content = self._strip_frontmatter(content)

    if include_references:
        refs_dir = skill_dir / "references"
        if refs_dir.exists():
            for ref_file in sorted(refs_dir.glob("*.md")):
                ref_content = ref_file.read_text()
                ref_content = self._strip_frontmatter(ref_content)
                # 追加参考文档
                content += f"\n\n===== Reference: {ref_file.stem} =====\n\n{ref_content}"

    return content

def load_combined(self, *skill_names: str) -> str:
    parts = []
    for name in skill_names:
        content = self.load_skill(name, include_references=True)
        parts.append(f"===== {name} =====\n\n{content}")
    return "\n\n".join(parts)
```

Bug 4 的根因：最初用 --- 作为子技能之间的分隔符。但 markdown 水平线也是 ---，SKILL.md 正文里有多处水平线用于视觉分隔。当 load\_combined() 用 --- 分割合并后的内容时，正文里的水平线会被误识别为分隔符，导致某些子技能的内容被截断。

修复方案：改用 ===== skill-name ===== 作为分隔符。这个格式在 markdown 里非常罕见，不会和正文内容冲突。同时，===== 在文本里视觉上很明显，调试时容易识别各子技能的边界。

## Bug 1：子技能从未加载

这是整个项目里最严重的 Bug，影响了系统的核心功能。原始代码：

```plain
# runner.py 原始代码（Bug 1）
self.system_prompt = self.skill_loader.load_skill(
    skill_name,                    # 只加载主技能
    include_references=False       # 连主技能的 references 都不加载
)
```

这段代码的问题：只加载了 code-review/SKILL.md 主技能，而 triage 规则、token budget 策略、review checklist、fix-PR 模板都在子技能里。对 LLM 来说，这些规则完全不可见。

效果：LLM 知道「要做 code review」，但不知道什么情况下该触发人工介入、每个文件 diff 截断多少字符、inline comments 要批量提交还是逐条提交、auto\_fixable 的判断标准是什么。LLM 只能靠自己的训练知识猜，行为完全不可控。

修复后的代码：

```python
# runner.py 修复后（Bug 1 修复）
self.system_prompt = self.skill_loader.load_combined(
    skill_name,                      # code-review（主技能）
    f"{skill_name}-triage",          # code-review-triage
    f"{skill_name}-analyze",         # code-review-analyze
    f"{skill_name}-act",             # code-review-act
    f"{skill_name}-memory",          # code-review-memory
)
# 修复后 system prompt 从单一技能扩展到 40,466 chars
# 所有子技能规则对 LLM 完全可见
```

修复后的 system prompt 包含 5 个子技能的所有内容，总长约 40,466 chars。这才是 LLM 能正确执行四阶段 review 的前提。

# ToolRouter：工具分发与 dry-run 模式

tool\_router.py 是工具层和 Agent 层之间的桥梁，负责把 LLM 的 tool\_use 请求路由到对应的工具函数。

## 工具注册与分发

ToolRouter 维护一个工具名 -> 函数的映射表，LLM 调用工具时，tool\_router 根据工具名找到对应函数执行：

```python
# tool_router.py 工具注册
class ToolRouter:
    def __init__(self, github_tools, memory_tools, dry_run=False):
        self.dry_run = dry_run
        self.tools = {
            # GitHub 读操作（dry-run 模式下正常执行）
            "get_pull_request":        github_tools.get_pull_request,
            "get_pull_request_files":  github_tools.get_pull_request_files,
            "get_pull_request_comments": github_tools.get_pull_request_comments,
            "list_commits":            github_tools.list_commits,
            "get_file_contents":       github_tools.get_file_contents,
            "search_code":             github_tools.search_code,
            # GitHub 写操作（dry-run 模式下返回 mock 数据）
            "create_pull_request_review": github_tools.create_pull_request_review,
            "create_branch":           github_tools.create_branch,
            "create_or_update_file":   github_tools.create_or_update_file,
            "create_pull_request":     github_tools.create_pull_request,
            "add_pr_comment":          github_tools.add_pr_comment,
            # Memory 工具（dry-run 模式下读操作正常，写操作返回 mock）
            "memory_get_all":          memory_tools.get_all,
            "memory_add":              memory_tools.add,
            "memory_search":           memory_tools.search,
            "memory_get_developer_profile":    memory_tools.get_developer_profile,
            "memory_update_developer_profile": memory_tools.update_developer_profile,
            "memory_aggregate_patterns":       memory_tools.aggregate_repo_patterns,
        }
        # 写操作工具集合（dry-run 时跳过实际执行）
        self.write_tools = {
            "create_pull_request_review", "create_branch",
            "create_or_update_file", "create_pull_request", "add_pr_comment",
            "memory_add", "memory_update_developer_profile", "memory_aggregate_patterns"
        }
```

## dry-run 模式的工程价值

dry-run 模式是开发调试时最重要的功能。在开发新功能或修改 Prompt 时，你不希望每次测试都真的在 GitHub 上提交 review 或创建 Fix PR，那会污染真实仓库，而且 GitHub API 有速率限制。

dry-run 模式的行为：读操作（get\_pull\_request、get\_pull\_request\_files 等）正常执行，从 GitHub 获取真实数据；写操作（create\_pull\_request\_review、create\_branch 等）返回 mock 数据，不真正调用 GitHub API。

```python
# dry-run 模式的 execute 方法
def execute(self, tool_name: str, tool_input: dict) -> dict:
    if self.dry_run and tool_name in self.write_tools:
        # 返回 mock 数据，让 LLM 以为操作成功了
        return {"status": "ok", "dry_run": True, "tool": tool_name, "input": tool_input}

    # 正常执行工具
    tool_fn = self.tools.get(tool_name)
    if not tool_fn:
        return {"error": f"Unknown tool: {tool_name}"}

    try:
        result = tool_fn(**tool_input)
        # 截断大型响应（防止 context overflow）
        result = self._truncate_result(tool_name, result)
        return result
    except Exception as e:
        return {"error": str(e), "tool": tool_name}
```

## 截断策略：防止 context overflow

这是 token budget 控制的具体实现。GitHub API 返回的数据可能很大，特别是 diff 文件和完整文件内容，不加限制会超出 context window：

```python
# tool_router.py 截断策略
MAX_PATCH_CHARS = 3000        # 每个文件的 diff 截断上限（约 100-150 行代码）
MAX_FILE_CONTENT_CHARS = 5000 # 完整文件内容截断上限（约 150-200 行代码）

def _truncate_result(self, tool_name: str, result):
    if tool_name == "get_pull_request_files" and isinstance(result, list):
        for f in result:
            patch = f.get("patch", "")
            if len(patch) > self.MAX_PATCH_CHARS:
                truncated = len(patch) - self.MAX_PATCH_CHARS
                f["patch"] = patch[:self.MAX_PATCH_CHARS] + \
                    f"\n... [truncated {truncated} chars, {truncated//50} lines approx]"

    elif tool_name == "get_file_contents" and isinstance(result, dict):
        content = result.get("content", "")
        if len(content) > self.MAX_FILE_CONTENT_CHARS:
            result["content"] = content[:self.MAX_FILE_CONTENT_CHARS] + "\n... [truncated]"

    return result
```

截断后 LLM 能看到文件的前 3000 字符（通常包含函数签名、主要逻辑），对于大多数安全漏洞和 bug 来说足够了。如果 LLM 认为需要看完整内容，可以再调用 get\_file\_contents 工具，这次只针对该文件，上限是 5000 字符。

# 轨迹记录系统

每次 review 运行时，TrajectoryLogger 同步记录所有事件到 JSONL 文件。这是整个数据合成 pipeline 的基础。

## JSONL 格式选择的理由

为什么选 JSONL 而不是 JSON 或数据库？

* 可以流式追加（append）：每个事件发生时立即写入一行，不需要等整个 review 完成再写文件。如果 review 中途失败，已写入的部分不会丢失。
* 可以流式读取：导出训练数据时，不需要把整个文件加载到内存，逐行读取处理即可。对于几百 MB 的轨迹文件，这非常重要。
* 人类可读：可以用 jq 命令快速查询，比如 cat trace\_xxx.jsonl | jq 'select(.type=="tool\_result")' 查看所有工具调用结果。
* 格式灵活：每行可以有不同的 schema（session\_start 和 tool\_result 的字段完全不同），不需要预先定义统一的 schema。

## 轨迹文件结构示例

一个典型的 trace\_abc123.jsonl 文件，每行一个 JSON 对象：

```json
{"type":"session_start","session_id":"abc123","pr":"owner/repo#42","timestamp":"2026-04-21T10:00:00Z","model":"claude-opus-4-6"}

{"type":"user","message":{"role":"user","content":"请对这个 PR 进行 code review: https://github.com/owner/repo/pull/42"}}

{"type":"assistant","message":{"role":"assistant","stop_reason":"tool_use","content":[
  {"type":"thinking","thinking":"先获取 PR 的基本信息，了解改动范围和文件列表..."},
  {"type":"text","text":"我来分析这个 PR，先获取基本信息。"},
  {"type":"tool_use","id":"tool_001","name":"get_pull_request",
   "input":{"owner":"owner","repo":"repo","pull_number":42}}
]}}

{"type":"tool_result","tool_use_id":"tool_001","tool_name":"get_pull_request",
 "result":{"title":"Fix SQL injection in user views","additions":15,"deletions":3,
           "changed_files":2,"state":"open","head_branch":"fix/sql-injection"}}

{"type":"session_end","stats":{
  "decision":"REQUEST_CHANGES","issues_found":2,
  "llm_calls":9,"tool_calls":14,"duration_ms":87430,"iterations":9

```

session\_end 里的 issues\_found 是 Bug 3 修复的关键字段。原始实现里这个字段始终为 0，导致 DPO 评分完全依赖 decision 字符串。修复方案是在 review 完成后，用正则扫描所有 assistant 消息，找到包含 issues: \[...] 的 JSON 块，解析 len(issues) 赋值给 issues\_found。

# 四阶段审查流程详解

整个 code review 流程被拆解为四个明确的阶段，每个阶段对应 Agent 主循环里的若干轮迭代。这四个阶段不是硬编码的状态机，而是通过 SKILL.md 里的指令引导 LLM 自主执行的。

## Phase 1：Triage 分类

Triage 阶段的核心问题只有一个：这个 PR 适合自动 review 吗？

为什么要有这个阶段？直接开始 review 不行吗？有几个原因：

* 成本控制：一次完整的 review 要调用 10+ 次 LLM 和 GitHub API，如果 PR 本来就不适合自动处理（比如是数据库 migration），浪费了资源还可能给出错误意见。
* 风险控制：涉及认证、权限、安全核心模块的 PR，自动 review 给出错误判断（比如漏掉安全漏洞）比不 review 更危险。
* 用户体验：如果 PR 是 draft 或者标题含 \[WIP]，说明作者还没准备好接受 review，这时候自动提交 review 会打扰作者。

Triage 判断规则（来自 code-review-triage/references/triage-rules.md）：

这些规则是 LLM 的参考依据，不是硬编码的 if-else 判断。LLM 读到这些规则后，调用 get\_pull\_request 获取 PR 信息，自主判断是否适合自动 review。这样的好处是：规则里没有覆盖到的边界情况，LLM 可以用常识判断，而硬编码规则遇到边界情况只会给出错误结果。

## Phase 2：Analyze 数据采集

Analyze 阶段的目标是采集 review 所需的所有上下文。这个阶段有两个关键设计：并发采集和 token budget 控制。

### 并发采集策略

Agent 在这个阶段会依次调用多个工具，采集不同维度的信息：

* get\_pull\_request\_files：获取所有改动文件的 diff（patch），了解具体改了什么代码。每个文件的 patch 截断到 3000 字符，防止 context overflow。
* list\_commits：获取最近 10 条提交记录，了解这个 PR 的开发历史，判断是否有反复修改同一处的迹象（可能说明存在未解决的问题）。
* get\_pull\_request\_comments：获取已有的 review comments，避免重复指出别人已经指出的问题。
* memory\_get\_all：读取团队规则库，获取已知问题模式、误报规则、团队代码规范。这是 Memory 系统的核心价值——让 Agent 知道「这个团队对哪类问题特别敏感」。
* get\_file\_contents（按需）：对于 diff 里涉及的高风险文件，获取完整文件内容做深度分析。这不是每次都调用，而是 LLM 判断需要时才调用。

### token budget 控制的重要性

随着 review 轮次增加，messages 列表会越来越长。到第 10 轮时，messages 可能已经包含几万 token。如果不控制，会超出 Claude 的 context window 上限（claude-opus-4-6 是 200K tokens）。

具体控制策略：

```markdown
# 各工具的 token budget 控制
工具名                      截断策略                        原因
----------------------------------------------------------------------
get_pull_request_files     patch 截断到 3000 chars/文件    diff 可能很长，优先看改动核心
get_file_contents          content 截断到 5000 chars       完整文件可能有几千行
list_commits               最多返回 10 条                  更早的提交与当前 PR 关联度低
memory_get_all             摘要模式，3000 tokens 上限       规则库可能很大，全量加载浪费 token

# 为什么 diff 截断比 file content 截断更严格？
# diff 里每行都有 +/- 前缀，实际代码密度比完整文件低
# 3000 chars 的 diff 大约对应 80-100 行有效改动
# 完整文件 5000 chars 大约对应 150-200 行代码
```

## Phase 3：Review 分析

这是整个 review 流程里 LLM 工作量最大的阶段。LLM 基于采集到的所有数据，按四个优先级发现问题，输出结构化 JSON。

### 问题优先级与发现策略

SKILL.md 里规定了四个优先级，LLM 按这个顺序检查：

1. 安全漏洞（severity: critical）：SQL 注入、XSS、命令注入、硬编码密钥/密码、不安全的反序列化、路径遍历。这类问题优先级最高，发现一个就必须 REQUEST\_CHANGES。
2. 逻辑 Bug（severity: high）：空指针访问、数组越界、条件判断错误、异常未处理、资源泄漏。这类问题可能在生产环境导致崩溃，必须修复。
3. 规范问题（severity: medium）：命名不规范、函数过长、缺少类型注解、注释缺失。这类问题影响代码可维护性，建议修复但不强制。
4. 性能优化（severity: low）：N+1 查询、不必要的循环、可以缓存的重复计算。这类问题建议关注但不阻塞合并。

### 结构化输出格式

LLM 的分析结果必须是严格的 JSON 格式，这样才能被程序解析和处理：

```json
{
  "issues": [
    {
      "severity": "critical",
      "category": "security",
      "file": "app/views.py",
      "line": 42,
      "description": "SQL 注入：使用 f-string 拼接 SQL 查询，攻击者可通过构造特殊输入执行任意 SQL",
      "suggestion": "改用参数化查询：cursor.execute('SELECT * FROM users WHERE id = %s', (user_id,))",
      "auto_fixable": true,
      "fix_code": "# 完整的修复后文件内容（不是代码片段，是整个文件）..."
    },
    {
      "severity": "high",
      "category": "bug",
      "file": "utils/db.py",
      "line": 78,
      "description": "未处理数据库连接异常，连接失败时函数返回 None，调用方没有检查 None",

      "auto_fixable": false,

    }
```

### auto\_fixable 的判断标准

auto\_fixable 字段决定了这个 issue 是否会触发 Fix PR 的创建。这个字段的设计有严格的约束，不能随意设为 true：

为什么要这么严格？因为 Fix PR 是直接写入代码仓库的。如果 auto\_fixable 判断错误，Agent 可能对一个逻辑错误生成错误的修复代码，比原来的 bug 更难发现。宁可少修复，不能错误修复。

## Phase 4：Act 执行

Act 阶段根据 review 结果执行具体操作，分四个分支：

### 分支 A：批量提交 inline review comments

这是 Bug 2 的修复所在。GitHub PR review 的正确提交方式是把所有 inline comments 和 review event 原子绑定：

````python
# 正确做法（Bug 2 修复后）：所有 comments 一次性传入 create_review
review = pr.create_review(
    body="## Code Review 摘要\n\n发现 2 个问题，需要修复后才能合并",
    event="REQUEST_CHANGES",    # APPROVE / REQUEST_CHANGES / COMMENT
    comments=[
        {
            "path": "app/views.py",
            "line": 42,
            "body": "🔴 **[Critical] SQL 注入风险**\n\n使用 f-string 拼接 SQL 查询，攻击者可通过构造特殊输入执行任意 SQL 命令。\n\n建议改用参数化查询：\n```python\ncursor.execute('SELECT * FROM users WHERE id = %s', (user_id,))\n```"
        },
        {
            "path": "utils/db.py",
            "line": 78,
            "body": "🟠 **[High] 未处理数据库异常**\n\n连接失败时函数返回 None，调用方没有检查返回值。建议添加异常处理。"
        }
    ]
)

# 错误做法（Bug 2 修复前）：逐条提交，comments 和 review event 脱节
# for comment in comments:
#     pr.create_review_comment(body=..., commit=..., path=..., line=...)
# pr.create_review(body=body, event=event)  # 两个独立操作，GitHub 显示混乱
````

为什么逐条提交是错误的？GitHub 会把 create\_review\_comment 的调用和 create\_review 的调用显示为两个独立事件：先是一堆孤立的 comments，然后才是 review 状态变更。在 PR 页面上，comments 和 review 没有关联关系，用户看到的是混乱的时间线。正确做法是把 comments 作为参数传给 create\_review，这样 GitHub 把它们绑定为同一个 review 事件。

### 分支 B：创建 Fix PR（仅对 auto\_fixable issues）

Fix PR 的创建是一个多步骤的 GitHub API 操作序列：

```python
# Step 1：创建修复分支（基于原始 PR 的 head 分支）
create_branch(
    branch="auto-fix/pr-42-20260421",
    from_branch=pr_info["head_branch"]   # 基于 feature 分支，不是 main
)

# Step 2：逐文件写入修复内容（必须先获取文件的 sha）
for issue in auto_fixable_issues:
    # 先获取当前文件的 sha，防止并发写入冲突
    file_info = get_file_contents(
        path=issue["file"],
        branch="auto-fix/pr-42-20260421"
    )
    # 写入修复后的完整文件内容（不是代码片段）
    create_or_update_file(
        path=issue["file"],
        content=issue["fix_code"],    # LLM 生成的完整文件内容
        sha=file_info["sha"],         # 必须提供，否则 GitHub 报 409 Conflict
        message=f"fix({issue['category']}): {issue['description'][:50]}",
        branch="auto-fix/pr-42-20260421"
    )

# Step 3：创建 Fix PR，合并回原始 feature 分支（不是 main）
create_pull_request(
    title=f"[Auto Fix] PR #{pr_number}: {', '.join(categories)}",
    head="auto-fix/pr-42-20260421",
    base=pr_info["head_branch"],   # 注意：base 是 feature 分支，不是 main
    body="自动修复以下问题：\n" + "\n".join(f"- {i['description']}" for i in auto_fixable_issues)
)
```

一个重要细节：Fix PR 的 base 是原始 PR 的 head\_branch（feature 分支），不是 main。这样 Fix PR 合并后，修复内容会进入 feature 分支，原始 PR 就可以合并了。如果 base 设为 main，Fix PR 和原始 PR 会有冲突，合并顺序也会混乱。

### 分支 C：critical 安全漏洞的特殊处理

发现 severity=critical 的安全漏洞时，除了提交 REQUEST\_CHANGES 之外，还会发送一条高优先级评论通知：

```plain

add_pr_comment(
    body="## ⚠️ 安全漏洞警告\n\n" +
         "本次 review 发现 **critical** 级别的安全漏洞，请在修复之前不要合并此 PR。\n\n" +
         "已创建 Fix PR：{fix_pr_url}（如果 auto_fixable=true）\n\n" +
         "如有疑问，请联系安全团队。"
)
```

### 分支 D：更新 Memory 知识库

每次 review 结束后，Agent 会更新 Memory 系统，把这次 review 的发现持久化：

* memory\_add：把新发现的问题模式添加到 known\_pattern 列表（如果这个模式之前没有记录过）。
* memory\_update\_developer\_profile：更新 PR 作者的 developer\_profile，增加 pr\_count，更新 issue\_history 里各类别的 count 和 last\_seen。
* memory\_aggregate\_patterns：把这次 review 的 issues 聚合到 repo\_pattern 统计里，更新 occurrence\_count 和 trend。

# 轨迹数据合成与训练格式

这是整个项目最有工程价值的部分。每次 review 运行产生一份 JSONL 轨迹文件，可以导出为三种不同的训练格式。

## 三种导出格式对比

## SFT 格式：native tool\_calls 的正确实现

SFT 数据的格式正确性是整个数据管道最关键的细节，也是 Bug 5 的所在地。

错误实现（Bug 5 修复前）：把 tool\_use 序列化成纯文本：

````sql
# 错误格式：tool_use 被序列化为纯文本字符串
{
  "role": "assistant",
  "content": "[Tool: get_pull_request]\n```json\n{\"owner\": \"owner\", \"repo\": \"repo\", \"pull_number\": 42}\n```"
}
# 问题：fine-tune 后的模型学到的是「输出这段文字」
# 而不是真正调用工具（function call）
````

这个格式在主流训练框架（LLaMA-Factory、verl、axolotl）里都有原生支持，不需要自定义 data collator。fine-tune 后的模型能真正学会「在什么时候调用哪个工具、传什么参数」，而不是学会输出某种文字格式。

## 工具调用监督格式

工具调用监督数据是 SFT 数据的补充，专门用于训练工具调用的时机和参数选择。每个 tool\_use -> tool\_result 对作为一条独立的训练样本：

```json
{
  "messages": [
    {
      "role": "system",
      "content": "你是一个代码审查 AI Agent，当前正在执行 Phase 2（数据采集阶段）..."
    },
    {
      "role": "user",
      "content": "PR #42 的基本信息已获取：改动了 2 个文件，共 15 行新增代码。请继续采集所需数据。"
    }
  ],
  "tool_call": {
    "name": "get_pull_request_files",
    "arguments": {"owner": "owner", "repo": "repo", "pull_number": 42}
  },
  "tool_result": {
    "files": [{"filename": "app/views.py", "patch": "+    query = f'SELECT...{user_id}'..."}]
  }
}
```

这种格式的优点是数据量大：一个 session 里有 12-15 次 tool\_call，就能产生 12-15 条工具监督样本，而 SFT 格式只产生 1 条。

## DPO 偏好对构建

DPO（Direct Preference Optimization）训练需要偏好对数据：同样的 prompt，一个更好的回复（chosen）和一个更差的回复（rejected）。

### 质量评分公式

每条轨迹的质量评分决定它在偏好对里是 chosen 还是 rejected：

```python
# DPO 质量评分公式（trajectory/exporter.py）
def quality_score(candidate: dict) -> float:
    score = 0.0

    # decision 权重：REQUEST_CHANGES 最有价值，APPROVE 可能是漏检
    decision_weights = {
        "REQUEST_CHANGES": 3.0,   # 发现问题并要求修改
        "COMMENT":         1.0,   # 只评论，没有明确要求修改
        "APPROVE":         0.0,   # 可能是漏检（issues_found=0 时尤其可疑）
    }
    score += decision_weights.get(candidate["decision"], 0.0)

    # issues_found 权重：发现的问题越多，质量越高（上限 3 分，防止刷分）
    score += min(candidate["issues_found"] * 0.5, 3.0)

    return score

# 评分示例：
# REQUEST_CHANGES + 4 个 issues = 3.0 + 2.0 = 5.0 分 -> chosen
# REQUEST_CHANGES + 1 个 issue  = 3.0 + 0.5 = 3.5 分 -> 中间
# COMMENT         + 1 个 issue  = 1.0 + 0.5 = 1.5 分 -> 中间
# APPROVE         + 0 个 issues = 0.0 + 0.0 = 0.0 分 -> rejected
```

### Bug 3：issues\_found 始终为 0

DPO 评分公式依赖 issues\_found 字段，但原始实现里这个字段始终为 0，导致评分完全依赖 decision 字符串，偏好对质量很差。

根因：session\_end 记录里的 issues\_found 在 runner.py 里初始化为 0 后从未更新。LLM 把 issues 列表输出在 text 块里（不是工具调用），runner.py 没有解析这个 text 内容。

修复方案：review 完成后，用正则扫描所有 assistant 消息的 text 内容，找到包含 issues 数组的 JSON 块，解析 len(issues) 赋值给 issues\_found：

```python
# runner.py：从 LLM 输出中提取 issues 数量（Bug 3 修复）
import re, json

issues_found = 0
# 收集所有 assistant 消息的 text 内容
all_text = ""
for msg in messages:
    if msg["role"] == "assistant":
        for block in msg.get("content", []):
            if isinstance(block, dict) and block.get("type") == "text":
                all_text += block.get("text", "")

# 用正则找到包含 issues 数组的 JSON 块
for json_match in re.finditer(r'\{[^{}]*"issues"\s*:\s*\[', all_text):
    start = json_match.start()
    depth, end = 0, start
    # 用括号计数法找到对应的闭合括号
    for i, ch in enumerate(all_text[start:], start):
        if ch == '{': depth += 1
        elif ch == '}':
            depth -= 1
            if depth == 0:
                end = i + 1
                break
    try:
        parsed = json.loads(all_text[start:end])
        if isinstance(parsed.get("issues"), list):
            issues_found = max(issues_found, len(parsed["issues"]))
    except (json.JSONDecodeError, ValueError):
        pass  # LLM 输出格式不规范时跳过，继续扫描
```

### 配对策略

有了质量评分，配对策略决定哪两条轨迹组成一个偏好对：

* 按质量评分降序排列所有轨迹。
* 相邻样本两两配对：评分最高的和第二高的配对，第三高的和第四高的配对，以此类推。
* 要求 chosen 评分 > rejected 评分（同分的不配对，没有偏好信号）。
* 可选过滤：只保留 chosen 评分 >= 3.0 的偏好对（确保 chosen 确实是高质量的）。

理想的 DPO 数据是同一个 PR 的不同 review 配对（输入相同，输出质量不同），但这需要对同一个 PR 多次运行。当前方案用不同 PR 的 review 配对，是工程上的妥协。

# Memory 系统：从单次工具到有学习能力的系统

Memory 系统是这个项目区别于普通 code review bot 的核心差异点。一个没有记忆的 Agent 每次 review 都从零开始，不知道这个团队对什么问题特别敏感，不知道某个开发者上周刚被指出过同样的问题，不知道这个仓库里 SQL 注入已经出现了 7 次。Memory 系统解决的就是这个问题。

## 存储格式与选型

所有记忆数据存储在 \~/.claude/review\_memory.jsonl，每行一条记录。选择 JSONL 而不是 SQLite 或 Redis 的理由：

* 零依赖：不需要安装数据库，文件即存储。对于个人开发者或小团队，这大大降低了部署成本。
* 可移植：整个记忆库就是一个文件，可以直接复制、备份、分享给团队其他成员。
* 可调试：用 cat \~/.claude/review\_memory.jsonl | jq 'select(.type=="known\_pattern")' 就能查看所有已知问题模式，不需要数据库客户端。
* 可追加：每次 review 后追加新记录，不需要加锁，不需要事务。

局限：没有索引，全量扫描。当记录超过几千条时，memory\_get\_all 的性能会下降。改进方案是按 type 分文件存储，或者迁移到 SQLite（保持 JSON 格式的灵活性，同时支持索引查询）。

## 六种内存类型

前四种是基础类型，后两种是这个项目新增的扩展类型。新增的两种类型让 Agent 具备了跨 PR 学习能力。

# 开发者成长画像（Developer Growth Profile）

这个功能的核心想法是：同一个开发者的问题往往有规律。如果 Alice 连续三个 PR 都有 SQL 注入问题，第四次 review 时不应该只是再次指出「这里有 SQL 注入」，而应该说「Alice 你已经出现 4 次 SQL 注入了，建议在提交前用 bandit 扫描一下」。这才是有教育意义的 review。

## developer\_profile 数据结构

```json
{
  "type": "developer_profile",
  "content": {
    "author": "alice",
    "pr_count": 12,
    "issue_history": [
      {"category": "security", "count": 4, "last_seen": "2026-04-15T00:00:00Z"},
      {"category": "style",    "count": 8, "last_seen": "2026-04-20T00:00:00Z"},
      {"category": "bug",      "count": 2, "last_seen": "2026-03-10T00:00:00Z"}
    ],
    "strengths":    ["测试覆盖率高", "命名规范清晰", "函数职责单一"],
    "growth_areas": ["SQL 安全（已出现 4 次）", "异常处理"],
    "last_updated": "2026-04-21T00:00:00Z"
  }
}
```

各字段的设计理由：

* pr\_count：不是开发者在 GitHub 上的总 PR 数，而是被这个 Agent review 过的 PR 数。这个字段决定了 comment 的详细程度（新手多解释，老手直接说问题）。
* issue\_history：按 category 统计问题出现次数，而不是记录每个具体问题。这样可以发现规律（某类问题反复出现），而不是无意义的流水账。
* strengths：记录开发者的优点。review 时不只是指出问题，也要肯定做得好的地方。这在 comment 风格里体现为偶尔的正面反馈。
* growth\_areas：明确的成长方向，在 review summary 末尾追加个性化建议。

## Comment 风格的动态调整

根据 developer\_profile.pr\_count 判断经验等级，动态调整 comment 的详细程度：

| 经验等级 | 判断标准 | Comment 风格 |
| ---- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 新手 | pr\_count < 5 | 完整解释 + 示例代码 + 背景知识

                               "这里存在 SQL 注入风险。SQL 注入是指攻击者通过构造
                                特殊输入来执行任意 SQL 命令，可能导致数据泄露或删除。
                                建议改用参数化查询：
                                cursor.execute('SELECT \* FROM users WHERE id = %s', (user\_id,))
                                这是 Python DB-API 的标准做法，参数会被自动转义。" |
| 中级 | 5 <= pr\_count < 20 | 问题 + 简洁建议
                               "SQL 注入风险（L42），改用参数化查询：
                                cursor.execute('SELECT \* FROM users WHERE id = %s', (user\_id,))" |
| 资深 | pr\_count >= 20 | 一行指出问题
                               "L42: SQL 注入，参数化查询。" |

## 实现细节：memory\_update\_developer\_profile 工具

每次 review 结束后，Agent 调用这个工具更新开发者画像：

```python
# memory_tools.py：更新开发者画像
def update_developer_profile(self, author: str, issues: list, pr_url: str) -> dict:
    # 1. 读取现有画像（如果存在）
    profile = self._get_profile(author)

    # 2. 更新 pr_count
    profile["pr_count"] = profile.get("pr_count", 0) + 1

    # 3. 更新 issue_history（按 category 统计）
    for issue in issues:
        category = issue.get("category", "unknown")
        history = profile.setdefault("issue_history", [])
        # 找到对应的 category 记录并更新
        entry = next((h for h in history if h["category"] == category), None)
        if entry:
            entry["count"] += 1
            entry["last_seen"] = datetime.utcnow().isoformat() + "Z"
        else:
            history.append({"category": category, "count": 1,
                           "last_seen": datetime.utcnow().isoformat() + "Z"})

    # 4. 更新 growth_areas（count > 3 的 category 加入成长建议）
    growth_areas = []
    for entry in profile.get("issue_history", []):
        if entry["count"] >= 3:
            growth_areas.append(f"{entry['category']}（已出现 {entry['count']} 次）")
    profile["growth_areas"] = growth_areas

    # 5. 写回 JSONL 文件
    self._save_profile(author, profile)
    return {"status": "ok", "pr_count": profile["pr_count"]}
```

# 跨 PR 模式智能（Cross-PR Pattern Intelligence）

developer\_profile 追踪的是个人问题，repo\_pattern 追踪的是仓库级别的问题趋势。如果一个仓库里 SQL 注入已经出现了 7 次，说明这个团队在 SQL 安全上有系统性的知识缺口，需要的不是一次次在 PR 里指出，而是一次专项培训或者引入自动扫描工具。

## repo\_pattern 数据结构

```sql
{
  "type": "repo_pattern",
  "content": {
    "repo": "owner/repo",
    "pattern_name": "critical:security",
    "category": "security",
    "severity": "critical",
    "occurrence_count": 7,
    "affected_files": ["app/views.py", "services/db.py", "api/users.py"],
    "trend": "increasing",        # increasing / stable / decreasing / new
    "first_seen": "2026-03-01T00:00:00Z",
    "last_seen":  "2026-04-20T00:00:00Z"
  }
}
```

trend 字段的计算逻辑：比较最近 30 天的 occurrence\_count 和之前 30 天的 occurrence\_count。如果最近 30 天 > 之前 30 天，trend = increasing；如果差不多，trend = stable；如果减少了，trend = decreasing；如果是第一次出现，trend = new。

## health-report CLI 命令

health-report 命令读取 Memory 里的 repo\_pattern 数据，生成 markdown 格式的健康报告：

健康报告不调用 LLM，直接从 Memory 数据生成 markdown 表格。这样速度快（毫秒级）、成本低（不消耗 token）。如果想要更有洞察力的建议，可以把结构化数据传给 LLM 做一次解读，但这需要额外的 LLM 调用成本。

## memory\_aggregate\_patterns 工具的实现

```python
# memory_tools.py：聚合 repo_pattern 统计
def aggregate_repo_patterns(self, repo: str, issues: list) -> dict:
    updated_patterns = []

    for issue in issues:
        pattern_key = f"{issue['severity']}:{issue['category']}"

        # 查找现有的 pattern 记录
        existing = self._get_pattern(repo, pattern_key)

        if existing:
            # 更新现有记录
            old_count = existing["occurrence_count"]
            existing["occurrence_count"] += 1
            existing["last_seen"] = datetime.utcnow().isoformat() + "Z"

            # 更新受影响文件列表（去重）
            if issue.get("file") and issue["file"] not in existing["affected_files"]:
                existing["affected_files"].append(issue["file"])

            # 计算趋势（简化版：比较最近 30 天和之前 30 天）
            existing["trend"] = self._calculate_trend(repo, pattern_key)
            updated_patterns.append(existing)
        else:
            # 创建新记录
            new_pattern = {
                "repo": repo,
                "pattern_name": pattern_key,
                "category": issue["category"],
                "severity": issue["severity"],
                "occurrence_count": 1,
                "affected_files": [issue.get("file", "unknown")],
                "trend": "new",
                "first_seen": datetime.utcnow().isoformat() + "Z",
                "last_seen":  datetime.utcnow().isoformat() + "Z",
            }
            updated_patterns.append(new_pattern)

    self._save_patterns(repo, updated_patterns)
    return {"status": "ok", "updated": len(updated_patterns)}
```

## 生成的测试代码质量要求

SKILL.md 里对生成的测试代码有明确的质量约束：

* 覆盖正常路径：函数的主要功能在典型输入下应该正确工作。
* 覆盖边界条件：空值、零值、最大值、最小值、边界值。
* 覆盖异常路径：函数声明会抛出的异常，测试必须验证异常被正确抛出。
* 覆盖条件分支：函数里的每个 if 分支至少有一个测试用例。
* 外部依赖必须 mock：数据库、HTTP 请求、文件系统操作必须用 mock 替代，测试不应该有网络请求或文件写入。
* 不修改被测试的业务代码：只添加测试文件，不修改 app/ 或 src/ 里的代码。

```python
        raise ValueError("user_id must be positive")

from unittest.mock import patch, MagicMock
from app.services.user import get_user
from app.exceptions import UserNotFoundError

class TestGetUser:
    @patch("app.services.user.db")
    def test_get_user_success(self, mock_db):
        # 正常路径：用户存在
        mock_db.query.return_value = [{"id": 1, "name": "Alice", "email": "alice@example.com"}]
        result = get_user(1)
        assert result["id"] == 1
        assert result["name"] == "Alice"
        mock_db.query.assert_called_once_with(
            "SELECT * FROM users WHERE id = %s", (1,)
        )

    def test_invalid_id_zero(self):
        # 边界条件：user_id = 0
        with pytest.raises(ValueError, match="must be positive"):

    def test_invalid_id_negative(self):
        # 边界条件：user_id < 0
        with pytest.raises(ValueError, match="must be positive"):
            get_user(-1)

    @patch("app.services.user.db")
    def test_user_not_found(self, mock_db):
        # 异常路径：用户不存在
        mock_db.query.return_value = []
        with pytest.raises(UserNotFoundError, match="User 999 not found"):

    @patch("app.services.user.db")
    def test_db_error(self, mock_db):
```
