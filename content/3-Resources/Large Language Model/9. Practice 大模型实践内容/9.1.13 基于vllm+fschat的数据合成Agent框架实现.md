## 二、模型部署

> 首先我们要知道，为什么选择fschat+vllm的方式来部署模型？
> 这是因为FastChat 已经内置了对 vLLM 的支持，可以通过启动一个特殊的 `vllm_worker` 来实现这一点。vLLM 自身利用 Ray 来实现多机多卡的分布式张量并行。

* **启动Ray集群**

在Master Node上执行：

```shell
ray start --head --port=6379 --include-dashboard=true --dashboard-host=0.0.0.0
```

在所有其他Worker Nodes上执行：

```shell
ray start --address='<MASTER_NODE_IP>:6379'
```

* **在主节点上启动 FastChat 控制器**

```shell
# 读取配置文件中的地址
```

在 Ray 头节点上启动 `vllm_worker`，它会自动连接到 Ray 集群并利用所有资源。

## 三、数据合成Agent框架实现

### 3.1 API客户端容灾实现

> 与大模型进行成千上万次交互是数据合成的常态。网络波动、API超时、节点下线等，任何一个环节都可能导致整个流程中断。因此，项目首先构建了一个 `ResilientOpenAIClient`。
> 它不仅仅是一个简单的API封装，而是集成了两大核心能力：**自动重试** 和 **端点故障切换**。
> * **自动重试**：利用 `tenacity` 库，客户端可以优雅地处理瞬时错误。如果一次API调用失败，它不会立即放弃，而是会以wait\_exponential策略等待一段时间后重试，大大提高了成功率。
> * **故障切换**：更进一步，该客户端可以配置多个API端点。当一个端点在多次重试后仍然失败时，它会自动切换到下一个可用的端点，保证了整个流程的连续性。

```python
class ResilientOpenAIClient:
    def __init__(self, api_keys: Dict[str, str], addresses: List[str], resilience_config: Dict):
        # ... 初始化多个客户端实例 ...
        self.retry_decorator = retry(
            stop=stop_after_attempt(resilience_config.get('max_retries', 3)),
            wait=wait_exponential(...)
        )

    def create_chat_completion(self, *args, **kwargs):
        @self.retry_decorator
        def _attempt_to_call():
            try:
                client = self.clients[self.current_client_index]
                logging.info(f"尝试调用 API: {client.base_url}...")
                return client.chat.completions.create(*args, **kwargs)
            except Exception as e:
                logging.warning(f"调用失败: {self.clients[self.current_client_index].base_url} 错误: {e}，正在重试...")
                raise

        # 遍历所有客户端实例，实现故障切换
        for _ in range(len(self.clients)):
            try:
                return _attempt_to_call()
            except RetryError as e:
                logging.error(f"端点 {self.clients[self.current_client_index].base_url} 重试失败。")
                self.current_client_index = (self.current_client_index + 1) % len(self.clients)
                logging.info(f"切换到下一个客户端: {self.clients[self.current_client_index].base_url}")

        raise Exception("所有 API 端点在所有重试后均失败。")
```

### 3.2 Agent抽象基类

通过定义一个 `Agent` 抽象基类ABC，为所有数据生成策略建立了一个统一的规范。

这个 `Agent` 类强制所有子类（即各种生成策略）都必须实现 `generate` 和 `verify` 两个核心方法。更妙的是，它提供了一个 `run_generation_loop` 模板方法。这个方法封装了“**生成 -> 验证 -> (失败则)重试**”的通用逻辑。这不仅减少了代码重复，更重要的是，它确保了所有智能体都遵循这一至关重要的质量控制流程。

```python
# data.py: Agent 抽象基类
class Agent(ABC):
    def __init__(self, client: ResilientOpenAIClient, judge_client: ResilientOpenAIClient, config: Dict):
        # ...

    @abstractmethod
    def generate(self, task: Dict) -> Dict:
        """基于任务执行一次数据生成。"""
        raise NotImplementedError

    @abstractmethod
    def verify(self, generated_data: Dict) -> bool:
        """验证生成结果是否满足内部质量标准。"""
        raise NotImplementedError

    def run_generation_loop(self, task: Dict, max_attempts: int = 3) -> Dict:
        """生成-验证循环模板，确保各代理执行模式一致。"""
        for attempt in range(max_attempts):
            generated_data = self.generate(task)
            if self.verify(generated_data):
                return generated_data
        raise Exception(f"{max_attempts} 次生成尝试后未能生成有效实例。")
```

### 3.3 数据合成智能体

#### 3.3.1 Self-Instruct Agent

> `SelfInstructAgent` 的灵感来源于经典的 。它的核心思想是Self-Instruct 论文：**从一小撮高质量的“种子”指令出发，让模型模仿这些例子的风格和主题，创造出全新的指令。**
> 它的工作流程是：
> 1. **采样**：从现有的指令池中随机抽取几个例子。
> 2. **生成**：将这些例子作为in-context learning的示例给大模型，并要求它生成一个“全新且不同”的指令。

```python
def generate(self, task: Dict) -> Dict:
    sampled_seeds = random.sample(
        self.seed_tasks,
        min(len(self.seed_tasks), self.config['agents']['self_instruct']['num_instructions_to_sample'])
    )
    prompt_instructions = "\n\n".join([f"- {s['problem']}" for s in sampled_seeds])
    prompt = (
        f"基于以下指令示例，生成一条全新且与示例不同的指令。\n\n"
        f"示例：\n{prompt_instructions}\n\n新指令："
    )
    # ... 调用API ...
    new_instruction = response.choices[0].message.content.strip()
    return {"generated_problem": new_instruction}
```

> 然而，仅仅生成是不够的。如何保证“全新且不同”？这正是 `verify` 方法的用武之地。它引入了 **ROUGE-L 分数** 作为新颖性的度量指标。新生成的指令会与种子池中的所有现有指令计算相似度，只有当最大相似度低于预设阈值时，才认为这是一条合格的新指令。
> 这种机制有效地避免了mode collapse，确保了生成数据的多样性，让指令集不断向外围探索。

```python
def verify(self, generated_data: Dict) -> bool:
    new_instruction = generated_data["generated_problem"]
    all_instructions = [s['problem'] for s in self.seed_tasks]
    scores = [
        self.scorer.score(new_instruction, old)['rougeL'].fmeasure
        for old in all_instructions
    ]
    max_rouge_l = max(scores) if scores else 0
    # 只有当与现有指令的最大相似度低于阈值时，才通过验证
    if max_rouge_l < self.config['agents']['self_instruct']['rouge_l_threshold']:
        self.seed_tasks.append({"problem": new_instruction}) # 通过后，加入种子池
        return True
    return False
```

#### 3.3.2 Evol-Instruct Agent

> Evol-Instruct 来源于 [WizardLM](https://www.google.com/url?sa=E\&q=https%3A%2F%2Farxiv.org%2Fabs%2F2304.12244) 中的Evol-Instruct思想，对一个已有的指令进行 **Evolution**，使其变得更复杂或更具创造性。
> 演化分为两个方向：
> * **广度演化**：生成一个与原指令领域相似，但更罕见、更不寻常的新指令。
> * **深度演化**：通过增加约束、深化专业性、具体化场景等方式，提升原指令的难度和深度。

```python
strategy = random.choice(self.config['agents']['evol_instruct']['deepening_strategies'])
prompts = {
    "add_constraints": f"请为以下指令添加一个额外的约束或要求：\n{original}",
    "deepening": f"如果你是专家，请将以下指令改写得更专业、更深入：\n{original}",
    "concretizing": f"请将以下指令改写得更具体，例如添加具体场景：\n{original}",
    # ... 其他策略
}
prompt = prompts.get(strategy, prompts["add_constraints"])
```

> `EvolInstructAgent` 设计了一个精巧的 **两阶段验证流程**，并且引入了一个独立的 `judge_client` (通常是能力更强的模型，如GPT-4) 来扮演裁判角色。
> 1. **信息增益检查**：首先，裁判模型需要判断演化后的指令是否真的比原始指令更复杂、信息量更大。它会对比两个指令，并回答“Equal”或“Not Equal”。这避免了无效的同义改写。
> 2. **可解性检查**：指令不能变得过于复杂以至于无法解答。因此，生成模型会尝试回答演化后的指令。如果它的回答中包含“抱歉”、“我不能”等词语，或者回答过短，则认为该指令太难，验证失败。

#### 3.3.3 MCTS Agent

> 对于需要多步推理的复杂问题（如数学、逻辑），简单的指令生成是不够的。我们需要的是高质量的 **解题过程**，即CoT。`MCTSAgent` 为此而生，它创新性地将 **MCTS** 应用于文本生成。
> MCTS是一种强大的决策规划算法，常用于棋类游戏（如AlphaGo）。在这里，棋盘变成了“解题路径”，每一步棋则是生成下一个推理步骤。
> 它的流程极其精妙：
> 1. **Selection**：从根节点（空路径）出发，根据UCT公式（平衡探索与利用）选择最有潜力的路径向下探索。
> 2. **Expansion**：到达叶子节点后，让模型基于当前路径，生成几个可能的“下一步推理”。这些新步骤作为新节点扩展了搜索树。
> 3. **Simulation**：从一个新扩展的节点出发，让模型快速地“走到底”，生成一个完整的解。这步不求质量，只求快速获得一个结果。
> 4. **Backpropagation**：使用强大的裁判模型为模拟出的完整解答打分（1-5分），这个分数作为“奖励”沿着路径一路向上反馈，更新路径上所有节点的“胜率”和“访问次数”。

```python
# ... 3. 模拟 (Simulation)
sim_res = self.client.create_chat_completion(...)
final_sol = sim_res.choices[0].message.content

# ... 4. 反向传播 (Backpropagation)
judge_prompt = (
    f"[问题]\n{task['problem']}\n\n[解答]\n{final_sol}"
    "\n\n任务: 用 1-5 分评估解答质量，只返回整数分数。"
)
judge_res = self.judge_client.create_chat_completion(...)
score = int(judge_res.choices[0].message.content.strip())
reward = (score - 1) / 4.0  # 标准化到 [0,1]

# 更新路径上所有节点的访问和奖励
temp = sim_node
while temp:
    temp.visits += 1
    temp.wins += reward
    temp = temp.parent
```

### 3.4 SynthesisPipeline

> 1. **加载配置**：从 `config.yaml` 读取所有参数，包括模型地址、API密钥、Agent参数等。
> 2. **初始化环境**：创建 `generator_client` 和 `judge_client`，并实例化所有Agent。
> 3. **任务分发**：遍历输入文件夹中的任务文件（每个文件是一个JSON，指定了初始问题和要使用的 `synthesis_algorithm`）。
> 4. **执行与监督**：根据任务指定的算法，调用相应的Agent执行 `run_generation_loop`。
> 5. **最终裁决**：无论哪个Agent生成了数据，都会经过一个统一的、由Judge模型执行的最终评估，以JSON格式输出分数和理由。
> 6. **结果归档**：将原始任务信息、生成算法、生成数据以及最终评估结果，合并成一个完整的记录，写入输出文件。

```python
def run_pipeline(self):
    # ...
    with open(output_path, 'w', encoding='utf-8') as f_out:
        for i, task_file in enumerate(task_files):
            try:
                # ... 读取任务和算法 ...
                agent = self.agents.get(algo)
                # ...
                # 执行生成-验证循环
                generated_data = agent.run_generation_loop(task_data)
                # 执行最终的独立评审
                judgement = self._run_judgement(generated_data)
                # 组装最终记录
                final_record = {
                    "original_task_file": str(task_file.name),
                    "synthesis_algorithm": algo,
                    "generated_data": generated_data,
                    "final_evaluation": judgement
                }
                f_out.write(json.dumps(final_record, ensure_ascii=False) + "\n")
            except Exception as e:
                # ... 错误处理 ...
```
