# 数据领域 Agent Harness

数据领域的 Agent Harness 不能只照搬通用 coding harness。通用底座可以复用，但验证方式、权限边界、上下文组织和完成标准都需要重新设计。

## 核心判断

通用 harness 的基础已经相对稳定：agent loop、提示词/skills、工具调用、MCP、context 管理、项目说明文件和执行日志。但数据任务的对象不是本地代码文件，而是数据仓库、指标口径、业务实体、查询成本和权限边界。

因此，数据领域 harness 的关键不是“让 Agent 能查数据”，而是让 Agent 在可控边界内完成可信分析。

## 和 Coding Harness 的差异

| 维度 | Coding Harness | 数据领域 Harness |
|---|---|---|
| 验证方式 | 测试、lint、类型检查、CI | 查询可运行、口径可解释、结果可复核、异常已检查 |
| 风险位置 | 本地文件、repo、构建环境 | 数据仓库、生产表、权限、成本、敏感字段 |
| 上下文 | 用到再读文件和文档 | 需要持续携带 schema、指标定义、业务实体、血缘、样例查询 |
| 完成标准 | 测试通过或功能可验收 | 分析结论可信、计算口径明确、数据质量已交代 |
| 隔离方式 | sandbox、分支、测试环境 | 只读权限、审批门、查询预算、危险操作拦截 |

## 设计原则

- 先抽取，再过滤，再补全，再验证，最后总结。不要一步到位生成结论。
- 默认只读。写表、删表、导出敏感数据都应该进入审批路径。
- 把指标定义、业务实体、表血缘、样例查询作为一级上下文，不要只塞自然语言背景。
- 对查询结果做数据质量检查：行数、空值、异常值、时间范围、分母、口径差异。
- 输出必须包含完成标准：跑了什么查询、如何验证、哪些异常没有覆盖。
- 把昂贵查询和跨域查询显式标记，避免 Agent 在探索中失控。

## 对个人工作流的启发

当前 Obsidian/Codex 的自动复盘也可以套用这套结构：

1. `extract`：先确定纳入范围和覆盖率。
2. `filter`：只选择高价值候选。
3. `enrich`：对缺信息的来源做回源/OCR/ASR。
4. `verify`：记录哪些信息可靠，哪些只是线索。
5. `summarize`：输出可读结论和待决策队列。

## Cubox Review 增补：AI 问数与 Text2SQL

数据问数不能只建一个“自然语言转 SQL”通道。更稳的设计是把问数拆成意图澄清、schema/指标检索、查询计划、SQL 生成、运行验证、结果解释六步。

### 需要显式管理的上下文

- 业务实体：用户、订单、账户、产品、渠道等实体之间的关系。
- 指标口径：时间窗口、分母、过滤条件、排除项。
- Schema 语义：字段含义、枚举值、主外键、样例行。
- 查询习惯：历史高质量 SQL、常见 join 路径、危险查询模式。
- 权限边界：敏感字段、跨域表、昂贵查询、写操作。

### 低证据线索

`AI 问数，不该只是把自然语言翻译成 SQL` 和 `AI智能问数工作流程` 两条源文主要依赖图片，当前只作为方向线索：问数系统应更像数据分析 harness，而不是单次 Text2SQL 模型调用。后续如果要做强结论，需要 OCR 或回源后补充具体流程。
