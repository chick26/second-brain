# Harness Engineering: 为 Agent 设计闭环系统

**一句话总结: Harness engineering 是在为llm构造一个可执行、可观测、可验证、可纠偏的外部闭环。** harness engineering 关心的是 **模型能做什么、怎样收到反馈、失败后如何继续、系统如何防止错误扩散。** OpenAI 对 Codex 的描述为：长任务的稳定性不是来自一个更长的 prompt，而是来自一套持续循环的 agent loop；而在使用自定义工具时，真正负责跑工具和接回结果的，正是 client 侧的 harness。

## 一、爆火的原因

OpenAI 用 5 个月、几名工程师起步让 Codex 驱动一个内部 beta 产品，而且人类不直接写代码，主要工作转为“补工具、补约束、补文档、补验证”。

我认为这件事的本质是，**大模型的使用范式，正在从单步问答，切到轨迹优化。** 在单步问答里，我们优化的是一次输出；在 agent 场景里，我们优化的是一条轨迹：规划、读文件、调工具、看报错、修复、再验证、最后结束。只要问题从“单轮生成”变成“多步执行”，模型就不再只是一个 conditional generator，而更像一个被放进环境里的策略。这个时候，真正决定性能的，不只是模型权重，还包括它能观察到什么状态、能采取哪些动作、每一步能得到什么反馈。这个“环境设计”本身，就是 harness engineering。

## 二、Harness Engineering 和 Prompt / Context Engineering 的边界

Thoughtworks 对 context engineering 的定义很简洁：它是在整理“模型应该看到什么”，目标是让模型得到更好的结果；并且他们明确提醒，context 不是越多越好，过多上下文会拖垮效果和成本。

但 harness engineering 比这再往前走了一层。

**Context engineering 解决的是输入分布。**
比如规则文件、skills、MCP、repo 文档、历史对话、文件树。这些都在决定模型看到的状态表示。

**Harness engineering 解决的是闭环动力学。**
 它不仅决定输入，还决定：

* 模型有哪些动作空间；
* 动作执行后返回什么形式的观察；
* 哪些约束是靠 prompt 提醒，哪些是靠程序硬性拦截；
* 什么时候继续迭代，什么时候终止；
* 长时运行时如何做状态压缩、记忆迁移、错误恢复。

## 三、算法认知

### 1. 它本质上是在做外部 reward shaping

一旦 agent 犯了一个错，就工程化地让它以后不要再犯。

具体做法只有两类：改 `AGENTS.md` 这类隐式提示，或者直接加工具，比如截图脚本、过滤测试脚本等。

从算法视角看，这其实就是 **把稀疏、延迟、主观的人类反馈，改写成局部、快速、可验证的外部反馈信号**。原来人类在最后 PR review 阶段才发现“命令跑错了”“依赖方向乱了”“UI 崩了”，现在这些问题被前移成 lint、结构测试、边界校验、截图比对、browser run、日志检查、质量分数更新。也就是说，harness 的真正作用不是“帮模型多做几件事”，而是 **把错误尽量转成 machine-checkable signal，让策略在轨迹中更早地收到惩罚或修正。**

这和 RL 里的 reward shaping 很像，但它不是训练时做，而是 **推理时通过环境把 reward 外显出来**。这也是我认为它最有价值的地方：你不必重新训一个模型，也能大幅改变它的行为分布。

### 2. 动作空间设计

很多团队谈 agent，还是停留在“给模型一个 shell”这个阶段。 在 Codex Prompting Guide 里，官方直接把“更新工具”列为迁移 harness 的主要抓手之一，还强调 apply\_patch、tool naming、parallel tool calling、truncation 等细节会显著影响效果。

这件事非常像策略学习里的 action abstraction。一个高质量工具不是“把 shell 包一层”就结束了，而是要满足三点：

第一，**语义清晰**。工具名、参数名、返回值都要接近模型训练分布，避免歧义。
 第二，**粒度合适**。太原子，轨迹过长；太粗暴，失败不可定位。
 第三，**结果可消费**。返回给模型的不是一堆噪声日志，而是对下一步决策有信息增益的 observation。

很多 agent 失败，并不是模型不会，而是 action space 设计得太差，导致策略永远在错误的中间表示上打转。

### 3. 可观测状态构造

O家在 harness engineering 中会反复强调一个词：**legibility**。一开始是让 UI、日志、指标对 agent 可读；后来进一步提出，整个仓库都应该优先为 agent 可读而组织，`AGENTS.md` 只是目录，真正的知识库在 `docs/` 里，作为 system of record。

我非常认同这一点。很多团队以为 agent 能力差，实际上是 **状态不可见**。
 你让模型改一个页面，但：

* 埋点规范分散在 wiki；
* 设计约束只存在 reviewer 脑子里；
* 线上报错在另一个系统；
* 依赖边界没人写清；
* 历史决策没有沉淀到 repo。

这种环境里，模型再强也只能“猜”。而一旦状态可见，模型的有效推理深度会大幅提升。因为对 agent 来说，**上下文不是信息总量，而是决策可达性。**

### 4. 硬约束与软约束分层

实际上，这套 harness 混合了 context engineering、architectural constraints 和 garbage collection 三类机制。

这是一个很重要的工程哲学：**能机械化的，不要只写成 prompt；必须依赖判断的，再交给模型。**

OpenAI 也是这么干的：文档只负责说明，真正的依赖方向、层次边界、跨域访问规则，用 custom linters 和结构测试去硬性约束。甚至他们强调，不是去微观规定实现细节，而是只强制 invariants。

我自己的判断是：

* prompt 适合表达 **偏好**；
* docs 适合表达 **知识**；
* tests / linters / schemas 适合表达 **不变量**；
* background cleanup 适合表达 **熵管理**。

把这些东西全塞进系统提示词，是最常见也最低效的做法。

### 5. 它本质上是在做熵控制

完全 agent 自治会复制仓库里已有模式，哪怕这些模式并不优雅；早期openai每周要花 20% 时间清理 “AI slop”，后来改成把 golden principles 编进仓库，并跑周期性后台任务扫描偏离、更新质量分、发起小型重构 PR。

这在算法上其实很像 **online policy drift control**。
 一个 agent 不是只会犯“局部错误”，它还会持续放大仓库里的历史偏差。只要错误模式被写进代码、文档、模板，它就会通过 retrieval 和 imitation 被再次采样出来，最后形成自我强化。

所以我一直认为，**长周期 agent 系统必须有 entropy budget 的概念。**
 不是只看一次任务成不成功，而要看：

* 错误模式复现率有没有下降；
* 同类修复是否在跨任务复用；
* 代码风格/结构分布是否在变窄还是变宽；
* 背景 refactor 是否持续压制新坏味道。

没有这层机制，agent 产能越高，技术债只会积得越快。

## 四、为什么说 Harness Engineering 是“算法问题”，不是纯工程问题

很多人会把 harness engineering 理解成“再写点脚本、再补点规则”。这个理解太浅。

在我看来，它至少包含四个很强的算法设计问题：

**第一，状态表示。**
 什么信息该进入当前步，什么信息只在需要时加载，什么信息必须压缩成长期记忆。这对应 context selection、memory compaction、tool-result truncation。OpenAI 官方也在 prompt guide 里专门强调 compaction、tool response truncation 和并行读取策略。

**第二，动作抽象。**
 工具该以什么粒度暴露，名字怎样命名，参数如何组织，何时允许并行，何时必须串行。这会直接改变模型的搜索效率与失败恢复路径。

**第三，验证器设计。**
 什么属于 deterministic check，什么属于 model-based review，什么必须 escalation to human。OpenAI 的运行方式本质上就是 agent 自审、额外 agent review、本地和云端多路反馈叠加，再进入下一轮。

**第四，终止条件。**
 什么时候算 done，不是语言层一句“我完成了”，而是构建通过、测试通过、关键路径验证通过、文档更新完成、review 问题闭合。没有 termination contract，agent 很容易产生“语义完成、工程未完成”的错觉。

所以，**Harness engineering 的核心不是“把模型接进系统”，而是把任务重写成一个可闭环优化的控制问题。**
