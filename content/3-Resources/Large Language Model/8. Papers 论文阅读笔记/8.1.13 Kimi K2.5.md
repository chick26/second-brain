## 1. 背景和意义

> 过去一年，多模态大模型的主线问题从 能看懂图片 扩展到三个更难的方向：
> 1. **原生多模态**：不是在强语言模型上后接视觉适配层，而是在预训练与后训练阶段让视觉与语言共同成长。
> 2. **长上下文与长视频**：多模态输入密度更高，真正落地任务常常是长文档、长网页、长视频、或大量截图/文件集合。
> 3. **Agentic intelligence**：真实任务需要搜索、验证、对比、多步工具调用与持续纠错。仅靠单轮对话的生成不够，必须具备稳定的多步执行。

## 2. 动机核心

### 2.1 视觉能力强化是否必然牺牲语言能力？

很多视觉适配路线隐含一个假设：语言先练到很强，再在后期用高比例视觉数据把视觉能力补上。

K2.5 的结论相反：**在固定视觉-文本 token 预算下，早期融合、较低视觉比例反而更好**。

![[_Attachments/Images/8.1.13 Kimi K2.5-image-1.png]]

> 这背后的工程意义非常直接：如果“视觉后置 + 高比例冲刺”并不占优，那么更合理的路线是 **从更早阶段就让视觉与语言共同收敛到统一表征**，减少后期对齐成本与能力撕裂。

### 2.2 Agent 走向复杂任务时，串行执行的延迟与上下文爆炸

> 传统单智能体 Agent 做复杂任务的瓶颈主要是两类：
> * **串行工具调用的延迟线性增长**：任务越复杂，步骤越多，端到端时延越高。
> * **长轨迹上下文爆炸**：浏览、搜索、代码执行产生大量中间信息；简单截断会损失关键结构信息。
> K2.5 的核心做法是 **Agent Swarm**：由一个可训练的 orchestrator 动态创建并调度多个子智能体并行执行，通过 **Parallel-Agent RL** 学会并行拆解与调度，并用 critical steps 把训练目标与并行时延对齐。

## 3. 模型结构详解

### 3.1 Kimi K2 MoE 语言模型

> K2.5 的语言侧建立在 Kimi K2 之上：一个 trillion-parameter 级别的 MoE Transformer。报告给出的关键配置是：**总参数约 1.04T，激活参数 32B，384 个 experts，每 token 激活 8 个 experts（稀疏度 48）**；并使用 MuonClip 与 QK-Clip 提升训练稳定性。
> 这里的重要点不是参数更大，而是 **稀疏激活带来的可扩展算力利用，** 为后续多模态、长上下文、RL 与 Agent 训练提供了更可控的计算预算。

### 3.2 MoonViT-3D + MLP Projector + K2 MoE

K2.5 的多模态结构由三部分组成：

* **MoonViT-3D**：原生分辨率视觉编码器
* **MLP projector**：视觉到语言 token 空间的映射
* **Kimi K2 MoE LLM**：统一解码与推理主体

#### 图像与视频共享表征空间

它把 `patch packing `的思想推广到时间维度：将最多四帧视为时空体，把 2D patch 展平并打包到同一个 1D 序列中，让同一套 attention 机制跨空间与时间工作，并通过轻量 `temporal pooling` 压缩时间维度以支持更长视频。不需要为视频单独引入复杂模块分叉，从机制上鼓励图像预训练知识自然迁移到视频。

### 3.3 原生多模态预训练策略

在固定总视觉-文本 token 预算下，**Early fusion + 10%:90% 视觉:文本比例** 在多个维度更优，尤其在 OCR 与视觉推理上优势明显。

| **策略** | **视觉注入时机** | **视觉:文本** | **视觉知识** | **视觉推理** | **OCR** | **文本知识** | **文本推理** | **代码** |
| ------ | ---------- | --------- | -------- | -------- | ------- | -------- | -------- | ------ |
| Early | 0% | 10%:90% | 25.8 | 43.8 | 65.7 | 45.5 | 58.5 | 24.8 |
| Mid | 50% | 20%:80% | 25 | 40.7 | 64.1 | 43.9 | 58.6 | 24 |
| Late | 80% | 50%:50% | 24.2 | 39 | 61.5 | 43.1 | 57.8 | 24 |

### 3.4 零视觉 SFT

一个容易被忽略但很关键的创新是 **zero-vision SFT**：不用高成本的图文标注链式思维数据，而是用纯文本 SFT，**通过在 IPython 里代理图像操作，让模型学到像素级操作风格的推理行为，并作为多模态 RL 的冷启动**。

此外还给出一个反直觉观察：**图文 SFT 在某些视觉 agentic 任务上反而更差**，原因推测是高质量视觉 SFT 数据不足。

### 3.5 Outcome-based 视觉 RL 与跨模态迁移

视觉 RL 训练从三类任务组织：视觉 grounding 与计数、图表与文档理解、依赖视觉输入的 STEM 问题。

更有价值的是 Table 2：视觉 RL 不仅提升视觉任务，还带来 **纯文本任务提升**（cross-modal transfer）。

| **Benchmark** | **Vision-RL 前** | **Vision-RL 后** | **提升** |
| ------------- | --------------- | --------------- | ------ |
| MMLU-Pro | 84.7 | 86.4 | 1.7 |
| GPQA-Diamond | 84.3 | 86.4 | 2.1 |
| LongBench v2 | 56.7 | 58.9 | 2.2 |

作者解释倾向于校准与结构化信息抽取能力增强，对类似计数、OCR 风格问题有泛化收益。

### 3.6 Token-efficient RL

> K2.5 强调 test-time scaling，但也指出预算约束训练会导致 **length-overfitting**：模型学会短推理但不会在更高 token 上继续扩展推理。于是提出 Toggle：在预算受限 phase与标准扩展 phase之间交替优化，并定义问题相关的预算估计。

### 3.7 Agent Swarm

![[_Attachments/Images/8.1.13 Kimi K2.5-image-6.png]]

> Agent Swarm 的结构要点是：
> * 训练时 **子智能体冻结**，仅更新 orchestrator，规避端到端 co-optimization 的 credit assignment 与不稳定性。
> * 通过奖励设计解决两类典型失败：
> * serial collapse：退化成单智能体
> * spurious parallelism：无意义刷并行度
> * 用 **critical steps** 衡量并行执行的 关键路径长度 ，让训练目标直接对齐时延，而不是对齐总步数。
> * 在上下文管理上，Agent Swarm 被描述为 主动上下文分片 ：把子任务隔离到子智能体局部上下文，只把必要结果回传 orchestrator，从结构上减少全局上下文污染。

## 4. 训练与推理流程

### 4.1 预训练流水线

![[_Attachments/Images/8.1.13 Kimi K2.5-image-5.png]]

> K2.5 的预训练分三段，并给出了数据形态、token 规模、序列长度与可训练组件：
> * **阶段 1：ViT Training（约 1T tokens，seq=4096）**
> 数据包括 alt text、合成 caption、grounding、OCR、视频等；MoonViT-3D 从 SigLIP 持续预训练，通过 caption generation 的 cross-entropy 方式对齐到 LLM。
> * **阶段 2：Joint Pre-training（约 15T tokens，seq=4096）**
> 从接近 K2 末期 checkpoint 继续，用额外混合视觉与文本 token 共同提升语言与多模态能力，并对代码数据加权。
> * **阶段 3：Joint Long-context Mid-training（约 500B + 200B tokens，seq=32k→128k 级别扩展）**
> 引入更高质量数据与长上下文激活，使用 YaRN 插值逐步扩展上下文窗，目标包括长文本理解与长视频理解。

### 4.2 SFT → 视觉 RL → 联合多模态 RL → Agent Swarm PARL

> * **SFT**：沿用 K2 的 SFT pipeline，并通过多模型合成候选、领域化数据管线、人标与多阶段校验构建大规模指令数据，强化互动式推理与工具调用。
> * **zero-vision SFT 冷启动**：为后续视觉 RL 与视觉工具调用提供可泛化的启动点。
> * **Outcome-based 视觉 RL**：围绕视觉必需任务做可验证奖励，逐步提升视觉推理稳定性，并通过自举数据管线继续扩展。
> * **联合多模态 RL**：按能力而不是按输入模态组织专家与奖励模型，最大化跨模态迁移。
> * **PARL 训练 Agent Swarm**：只训练 orchestrator，结合 critical steps 约束，把并行带来的质量提升与时延收益一起纳入优化目标。

## 5. 实验核心结论

### 5.1 评测设置

> **(1) 模型与模式设置**
> Kimi K2.5 与 DeepSeek-V3.2 使用 thinking；Claude Opus 4.5 使用 extended thinking；GPT-5.2 使用 xhigh reasoning effort；Gemini 3 Pro 使用高 thinking level。
> **(2) 解码与上下文**
> 除非另有说明，K2.5 评测使用 temperature=1.0、top-p=0.95，上下文长度 256k。
> **(3) 多次采样与 token budget**
> * HLE、AIME 2025、HMMT 2025、GPQA、IMO-AnswerBench 等任务给到最高 96k completion budget，并有 avg@32、avg@8 等多次采样设置。
> * 视觉任务普遍 max-tokens=64k，部分任务有多次运行平均。
> **(4) 工具与上下文管理策略差异**
> * HLE 的 tool-augmented 设置使用“只保留最近一轮工具消息”的简化上下文管理。
> * BrowseComp 给出两种设置：无上下文管理 vs 使用 Discard-all（超过阈值则截断全部历史）。
> * 许多基准中带 \* 的分数来自作者内部重测，不等同于公开 leaderboard。

### 5.2 文本推理与通用能力

| **Benchmark** | **K2.5** | **Claude Opus 4.5** | **GPT-5.2 (xhigh)** | **Gemini 3 Pro** | **DeepSeek-V3.2** |
| ----------------- | -------- | ------------------- | ------------------- | ---------------- | ----------------- |
| HLE-Full | 30.1 | 30.8 | 34.5 | 37.5 | 25.1† |
| HLE-Full w/ tools | 50.2 | 43.2 | 45.5 | 45.8 | 40.8† |
| AIME 2025 | 96.1 | 92.8 | 100 | 95 | 93.1 |
| HMMT 2025 (Feb) | 95.4 | 92.9\* | 99.4 | 97.3\* | 92.5 |
| IMO-AnswerBench | 81.8 | 78.5\* | 86.3 | 83.1\* | 78.3 |
| GPQA-Diamond | 87.6 | 87 | 92.4 | 91.9 | 82.4 |
| MMLU-Pro | 87.1 | 89.3\* | 86.7\* | 90.1 | 85 |
| SimpleQA Verified | 36.9 | 44.1 | 38.9 | 72.1 | 27.5 |
| AdvancedIF | 75.6 | 63.1 | 81.1 | 74.7 | 58.8 |
| LongBench v2 | 61 | 64.4\* | 54.5\* | 68.2\* | 59.8\* |

1. **数学推理处于第一梯队**：AIME 2025 为 96.1，HMMT Feb 为 95.4，IMO-AnswerBench 为 81.8。它并非每项都压过 GPT-5.2，但在开源模型里表现强势，且后面会看到 token 使用更克制（Table 5）。
2. **工具增强对“极难综合题”带来显著跃迁**：HLE-Full 从 30.1 提升到 50.2，绝对提升 20.1。这里的含义是：对 HLE 这种“信息密集、需要外部检索与验证”的任务，K2.5 的工具调用收益非常可观。
3. **知识型短问答存在明显短板信号**：SimpleQA Verified 只有 36.9，而 Gemini 3 Pro 达到 72.1。该差距通常意味着：在“短事实核验”这类题型上，模型的知识覆盖、置信度校准或拒答策略可能不够强，需要结合检索或更强的事实性约束。
4. **长上下文仍不是 SOTA**：LongBench v2 为 61.0，低于 Gemini 3 Pro 的 68.2\*。这与 K2.5 强调 256k 上下文并不矛盾：长上下文能力往往与数据配方、训练目标（检索式、定位式、汇总式）和评测提示强绑定，单看“窗口大小”无法保证得分。

### 5.4 工具增强与 Agentic Search

#### 5.4.1 上下文管理带来巨大增益

论文还在正文强调：在 BrowseComp 上，K2.5 使用 Discard-all 后显著超过 Claude 与 Gemini，并高于 GPT-5.2 报告值 65.8（注意该比较依赖评测设置可比性）。

**这里的技术含义**：在长轨迹浏览任务里，“模型会不会检索”只是第一步，“是否能管理工具历史、避免上下文污染”常常决定最终上限。

#### 5.4.2 Agent Swarm质量提升 + 并行加速

| **Benchmark** | **K2.5 Agent Swarm** | **K2.5 单智能体** | **Claude Opus 4.5** | **GPT-5.2** | **GPT-5.2 Pro** |
| -------------------- | -------------------- | ------------- | ------------------- | ----------- | --------------- |
| BrowseComp | 78.4 | 60.6 | 37 | 65.8 | 77.9 |
| WideSearch | 79 | 72.7 | 76.2 | — | — |
| In-house Swarm Bench | 58.3 | 41.6 | 45.8 | — | — |

论文明确指出：BrowseComp 上 Agent Swarm 78.4，相比单智能体绝对提升 17.8，并超过 GPT-5.2 Pro 77.9。

更关键的是 **并行节省时间**：Figure 8 显示在 WideSearch 的不同目标 Item-F1 下，Agent Swarm 相比单智能体达到目标的执行时间可快 3–4.5 倍，并且目标越高优势越明显。

#### 5.4.3 Agent Swarm 是主动上下文管理

论文把 Agent Swarm 与 Hide-Tool-Result、Summary、Discard-all 等被动截断策略对比，强调 Swarm 是把上下文拆成多个隔离工作区，只回传关键信息给 orchestrator，从而实现 context sharding。

> 这是一个非常实用的判断标准：当任务的失败主要来自上下文爆炸而不是单步能力不足时，提升单模型参数或延长窗口往往不如“结构化分片 + 选择性回传”有效。

1. **“更强且更短”在多项任务上同时成立**：AIME、HMMT、LiveCodeBench 都呈现性能上升或持平，同时 token 明显下降。对线上推理成本与延迟非常友好。
2. **GPQA 例外提示“更强≠更短”**：GPQA 上 K2.5 token 反而略高，这常见于“科学问答需要更长的自检与不确定性处理”。把 token 压到极短可能会损失可靠性。
3. **Toggle 的角色**：论文在 token-efficient RL 小节说明 Toggle 用于避免 rigid budget 的 length-overfitting，并在 K2 Thinking 上观察到平均输出 token 可下降约 25–30%，且性能影响很小（Figure 5）。
   尽管 Figure 5 直接展示的是 K2 Thinking，但它解释了 K 系列“在推理可扩展性与成本之间做训练期折中”的核心思想。
