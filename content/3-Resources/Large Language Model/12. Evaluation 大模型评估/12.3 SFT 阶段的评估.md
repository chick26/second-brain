# 从语言分布拟合到条件行为对齐

如果说预训练阶段评估的核心对象是无条件或弱条件的语言分布拟合能力，那么 **SFT** 评估的对象已经发生了本质变化。SFT 之后，模型不再只是一个尽可能逼近互联网文本语料分布的生成器，而是一个在 **用户指令**、**系统约束**、**任务上下文** 条件下产生 response 的策略。此时，评估问题也不再是 **模型是否更会续写**，而是 **模型是否按要求回答、是否完成任务、是否在开放式交互中表现出帮助性、真实性与边界感**。因此，预训练阶段常见的 **困惑度、token-level NLL**，至多只能作为辅助诊断指标，而不能再充当 SFT 成败的主判据。**SFT 评估的重心，必须从分布拟合转向条件行为质量**

# 1. SFT 改变了什么：评估对象从 $p_\theta(x)$ 变成 $p_\theta(y\mid x)$

在标准 SFT 中，训练数据通常由指令或对话上下文 $x$ 与期望响应 $y$ 构成，目标函数一般写作：

$\mathcal{L}_{\mathrm{SFT}} = -\mathbb{E}_{(x,y)\sim \mathcal{D}_{\mathrm{SFT}}} \left[ \sum_{t=1}^{|y|} \log \pi_\theta(y_t \mid x, y_{<t}) \right]$

这个目标仍然是交叉熵，但语义已经不同。预训练时，模型是在 **学习语言通常怎样继续**；SFT 时，模型是在 **学习面对特定任务指令时，什么样的响应更符合期望**。二者的差别看似只是条件项 x 的加入，实质上却意味着模型开始被拉向一个更窄、更人工、也更带有价值判断的目标分布。因此，**SFT 评估本质上是在度量条件行为对齐，而不是一般语言流畅性**

这也是为什么很多经过 SFT 的模型，在某些 base model 指标上未必继续提升，却在真实使用体验上显著变好的原因：SFT 会 **把概率质量重新分配到更符合指令、格式和对话风格的响应上**。对于用户而言，这种变化往往比无条件语言建模能力更重要。SFT 评估必须回答至少四个核心问题：

* **模型是否能准确理解并执行指令**
* **模型是否在开放式任务中更有帮助**
* **模型是否更真实，更少胡编**
* **模型是否在危险请求上保持合理拒答，而不是一味迎合**

# 2. 为什么预训练式指标不足以评 SFT

从形式上看，SFT 依旧最小化交叉熵，所以很多工作会顺手报告 validation loss。但在方法论上，这个做法的解释力是有限的。原因在于，**SFT 数据分布往往强依赖标注风格、模板格式、响应长度偏好和安全策略。** 于是，SFT validation loss 的下降，只能说明模型更拟合该 SFT 数据集本身，并不能直接推出它在开放世界指令上更有帮助。尤其在 **多轮对话、复杂约束、长响应任务** 中，token-level loss 与人类偏好、任务完成率之间并不存在稳定单调关系。**MT-Bench** 和 **Chatbot Arena** 之所以被提出，本质上就是因为传统闭集题目和简单 NLL 已不足以衡量聊天助手质量

更进一步，**SFT 的目标常常内含多个彼此张力很强的子目标。**

* 用户要求 **详细解释** 时，模型需要 **扩展**；但用户要求 **只回答 yes 或 no** 时，模型又必须 **压缩**
* 用户要求 **严格按 JSON 输出** 时，**风格自由度应被牺牲**；而用户要求 **自然聊天** 时，模型又不能 **机械僵硬**

这意味着 SFT 后模型质量不是单轴的：一个模型可能 **更礼貌却更啰嗦、更安全却更容易过度拒答、更擅长格式遵循却在开放式帮助性上退化**。因此，SFT 阶段比预训练阶段更需要 **分解式评估**，而不是只报一个总分

# 3. 指令遵循与约束满足：SFT 的第一性指标

从任务性质看，SFT 最直接、最基础的评估维度就是 **Instruction Following（指令遵循）**。这里 **最重要的不是答得像不像参考答案，而是是否遵守了用户显式提出的约束（例如长度要求、列表格式、关键词包含次数、大小写规范、是否只用一句话回答等），** 这类约束的优点是可程序验证，比开放式人工偏好更客观

**IFEval** 正是在这一思路下构建的，benchmark 包含约 500 个 prompts，并抽象出 25 类可自动检查的约束类型，特别适合衡量 SFT 后模型在精确约束执行上的能力。最自然的指标是严格约束满足率。设第 i 个样本包含 $m_i$ 个约束，约束验证函数为 $c_{ij}(y_i) \in \{0,1\}$，则 **prompt-level strict accuracy（衡量端到端可用性）** 可写作：

$\mathrm{Acc}_{\mathrm{prompt}} = \frac{1}{N}\sum_{i=1}^{N}\prod_{j=1}^{m_i} c_{ij}(y_i)$

若希望更细粒度分析是哪类约束最容易失败，也可定义 **instruction-level accuracy**：

$\mathrm{Acc}_{\mathrm{inst}} = \frac{\sum_{i=1}^{N}\sum_{j=1}^{m_i} c_{ij}(y_i)}{\sum_{i=1}^{N} m_i}$

但 **IFEval** 本身也暴露出一个重要问题：**随着模型变强，很容易被学会模式而非学会泛化所攻克**。**IFBench** 的贡献就在于指出，多数模型会对 IFEval 产生明显过拟合。**IFBench 引入了 58 个新的 out-of-domain 可验证约束**，直接把评估重点 **从是否记住常见模板转向是否真正掌握精确指令执行能力**

因此，SFT 的指令遵循评估至少应分成两层：

1. **In-domain precise IF**：IFEval 这类标准约束任务
2. **Out-of-domain generalization**：IFBench 这类未见约束测试
3. 二者结合，才能把会做题和会泛化区分开

# 4. 开放式帮助性评估：从参考答案比对转向偏好比较

SFT 的第二个核心目标是 **帮助性（Helpfulness）**。面对***写一封更自然的邮件***或***比较两种方案优缺点***这类问题，模型输出质量更多体现为相对偏好，而不是绝对正确。因此，评估逐渐从 **pointwise scoring** 转向 **pairwise preference comparison（成对偏好比较）**

最常见的量化方式是胜率（Win Rate）。设某模型与基线模型在 $N$ 个样本上逐对比较，记 win、loss、tie 的数量分别为 W, L, T，则：

$\mathrm{WinRate} = \frac{W + 0.5T}{N}$

为了衡量这种开放式帮助性，社区演化出了几条关键的主线：

* **AlpacaEval 2.0**：特别强调 raw win rate 之外还要控制长度偏差。自动评审模型往往 **系统性偏爱更长、更展开的回答**。其主要贡献是用回归式去偏方法削弱这种 verbosity bias，证明控制长度后，指标与真实人类排名的相关性更高
* **MT-Bench**：并不只看单轮回答，而是构造 80 个高质量多轮问题，覆盖 **写作、角色扮演、抽取、推理、数学、代码与知识问答等 8 类场景**。它的重点是多轮对话中的综合帮助性与稳定性，标志着社区开始系统性接受 **LLM-as-a-judge**
* **Arena-Hard-Auto**：随着旧基准区分度下降而提出，包含 500 个更困难的 prompts。相较 MT-Bench 具有约 3 倍更高的模型可分离性，并与人类偏好排名具有 98.6% 的相关性。SFT 评测必须随着模型能力演化而持续更新难度
* **WildBench**：从超过一百万条真实人机对话日志中筛选出 1024 个任务，提出 WB-Reward 与 WB-Score 两种自动评测方式。试图回到真实混乱的用户问题分布，避免模型仅仅在研究者熟悉的问题格式上刷高分

# 5. 真实性与事实性：SFT 是否真的减少了 *像真的假话*

很多 SFT 数据天然 **鼓励模型尽量回答**，这会带来副作用，**模型更像一个流畅的助手，但未必更真实**。SFT 可以显著提升帮助性感知，却未必同步提升 factuality（事实性）

* **TruthfulQA（抗误导真实性）**：包含 817 个问题，覆盖 38 个类别。专门针对人类常见误解和错误观念设计，测的是 **模型能否不去模仿训练语料中的错误信念**
* **SimpleQA（短事实准确性）**：包含 4326 个短事实型问题。让问题拥有单一、易判别的答案，降低了开放式事实评测中的模糊性

在形式上，事实性评测最简单的指标仍是准确率。但若评分体系允许拒答，则更合理的做法是把 **正确、错误、未作答** 三态分开统计：

$\mathrm{AttemptedAcc} = \frac{N_{\mathrm{Correct}}}{N_{\mathrm{Correct}} + N_{\mathrm{Incorrect}}}, \qquad \mathrm{AbstainRate} = \frac{N_{\mathrm{NotAttempted}}}{N}$

对 SFT 来说，这是一个极重要的区分：否则一个 **通过大量拒答来降低错误率的模型，可能被误判为更真实，但其实只是更不愿回答**

# 6. 安全性与拒答边界：该拒绝时必须拒绝

SFT 评估不能只看 helpfulness，还必须看 refusal quality。这里存在两类错误：第一类是 **under-refusal（拒答不足）**，面对有害请求仍然配合；第二类是 **over-refusal（过度拒答）**，对合法请求也动辄拒绝

在有害请求上的常见指标是 **ASR (Attack Success Rate)**。若给定恶意请求集合 $\mathcal{A}$，模型产生了可操作有害输出的样本数为 H，则：

$\mathrm{ASR} = \frac{H}{|\mathcal{A}|}$

* **HarmBench** 为自动化红队测试提供了一个标准化框架，强调统一框架和跨攻击方法的可比性
* **StrongREJECT** 则进一步尖锐地指出，以前很多 jailbreak 论文声称几乎 100% 成功，是因为评测基准过于宽松，系统性夸大了攻击效果。它提醒研究者：安全评估器也会失真，**有时 ASR 高仅仅是因为评测规则把“低可用性”的回答也算作了攻击成功**

完整的做法应同时定义 **benign over-refusal rate (ORR)**：

$\mathrm{ORR} = \frac{N_{\mathrm{Refuse\ on\ benign\ prompts}}}{N_{\mathrm{Benign\ prompts}}}$

一个通过见什么都拒绝来压低 ASR 的模型是毫无可用性的，**SFT 安全性是在风险控制和可用性之间寻找合理边界**

# 7. Judge-based evaluation 的方法学问题：评委也必须被评估

**SFT 评估越来越依赖 LLM-as-a-judge**，MT-Bench 的结果表明，强 judge 与人类偏好可达到 80% 以上的一致性。但这不意味着 judge 可以被无条件信任，评委模型往往带有以下系统性偏差：

* **位置偏差 (Position Bias)**：偏爱先出现的回答
* **长度偏差 (Verbosity Bias)**：偏爱更长、更展开的回答
* **自我强化偏差 (Self-enhancement Bias)**：对与自己风格相近的回答更宽容

更进一步，**JudgeBench** 的出现说明，在知识、数学和逻辑错误识别上，人类主观偏好本身可能就不是可靠真值。如果评委模型本身不可靠，那么我们优化出来的，可能不是更好的 assistant，而是更讨 judge 喜欢的回答风格

**代码实战：LLM-as-Judge Pairwise 评估与偏差控制**

```python
from openai import OpenAI
client = OpenAI()
def pairwise_judge(question: str, response_a: str, response_b: str, model: str = "gpt-4o") -> dict:
    """基础 Pairwise 评估逻辑 (Prompt 略)"""
    pass
# ── 偏差控制：交换位置重测 ──
def debiased_judge(question, resp_a, resp_b, model="gpt-4o"):
    """交换 A/B 位置各评一次，消除 position bias"""
    r1 = pairwise_judge(question, resp_a, resp_b, model)
    r2 = pairwise_judge(question, resp_b, resp_a, model)  # 交换位置
    # 如果两次一致，结果可信；否则标记为 TIE
    if r1["winner"] == "A" and r2["winner"] == "B":
        return "A"
    elif r1["winner"] == "B" and r2["winner"] == "A":
        return "B"
    else:
        return "TIE"
```

使用 judge-based evaluation 时，必须遵守三条原则：

1. **尽量采用 Pairwise 比较**
2. **对已知偏差进行显式控制（如位置交换）**
3. **定期使用 JudgeBench 校验评委本身**

# 8. 一个更严谨的 SFT 评估协议

一份合格的 SFT 评估报告，不应只写 我们在 MT-Bench 上提升了 0.4 分，而应采用多维度协议：

1. **精确指令执行**。IFEval (in-domain) + IFBench (out-of-domain)
2. **开放式帮助性**。MT-Bench、AlpacaEval 2.0 或 Arena-Hard-Auto，结合 WildBench 检查外部效度
3. **真实性**。TruthfulQA + SimpleQA
4. **安全边界**。HarmBench (测 ASR) + Benign 场景 (测 ORR)
5. **judge 质量**。补充 judge 选择理由、偏差控制方式及验证结果

SFT 评估必须是一个结构化、分维度、可解释的证据组合

# 9. 小结与实践指南

SFT 评估的主线不是困惑度，而是条件行为质量，执行 SFT 评估最重要的第一步是把任务拆分成上述四个维度。最推荐的执行 SOP 如下：

1. **先自建一个小型四维评测集（Baseline 定标）**：
   * *指令遵循*：自己构造一批简单但可检查的 prompts（如“只输出 JSON”、“不能超过 30 个词”），快速判断模型是没理解还是没执行。
   * *帮助性*：准备 30-100 个自己熟悉领域的问题。
   * *真实性*：准备一组答案单一明确、容易核查的短事实问答。
   * *安全边界*：准备两组数据，一组明显有害（测 under-refusal），一组敏感但合法（测 over-refusal）。
2. **再跑标准 Benchmark**：将你的自建集感受与自动化基准对比。
3. **人工与 Judge 交叉校验**：抽 30 到 50 个样本，看看人类打分和 LLM judge 的一致性如何，排查 Verbosity Bias。
4. **输出分维结论**：最后再汇总成“哪一类能力提升了，哪一类能力退化了”，而不是得到一个模糊的“整体好像更好了”
