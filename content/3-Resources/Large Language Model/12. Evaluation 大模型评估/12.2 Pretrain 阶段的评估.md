# 从语言建模拟合到可迁移能力测度

预训练阶段的评估与后续的 **SFT、RLHF 或 RAG、Agent** 评估在方法论上截然不同。预训练模型首先是一个 **自回归分布估计器**，其直接 **优化目标是下一个 Token 预测的负对数似然**。因此，这一阶段的核心问题不是模型像不像一个有用的助手*，*而是 **模型是否学到了更好的语言分布近似，并且这种拟合能否转化为跨任务的可迁移能力**

为了具备科学解释力，预训练评估不能只看 **单个下游分数或训练损失**，而应该从下面的 **三层评估框架** 着手：

1. **内在评估 (Intrinsic Evaluation)：** 衡量模型对 **文本分布的拟合质量**
2. **外在评估 (Extrinsic Evaluation)：** 衡量模型在标准化 **Zero-shot 或 Few-shot 设置下的泛化能力**
3. **可信度评估 (Reliability Evaluation)：** 检查 **分数是否受 Prompt、数据污染或统计波动的系统性影响**

# 1. 预训练评估的对象

从严格意义上讲，预训练阶段评估的对象不是聊天机器人，而是一个参数化语言分布 $p_\theta(x)$。如果训练目标是标准自回归建模，模型学习的是序列分解：

$p_\theta(x_{1:T}) = \prod_{t=1}^{T} p_\theta(x_t \mid x_{<t})$

> **🌟核心观点：受资源约束的统计估计比较**
> 评估一个预训练策略是否有效，绝不能脱离给定的计算预算。[**Scaling Laws**](https://arxiv.org/abs/2001.08361) 工作表明，语言 **模型损失随参数规模、数据规模和训练计算量呈现出稳定的幂律关系**，[**Chinchilla**](https://arxiv.org/abs/2203.15556) 工作进一步指出，模型 **参数量和训练 Token 数之间存在明显的 Compute-optimal 前沿**。预训练评估本质上是一种资源约束下的质量较量，而非脱离成本的绝对武力值竞赛

这个定义带来了两个重要推论：

* **必须绑定训练条件：** 一个在 300B Token 上训练的模型与在 3T Token 上训练的模型，即便参数量相近，其表现差异也不应被简单归结为架构优势，**必须同时报告模型性能与训练条件**
* **预训练评估必须区分分布内拟合与分布外迁移：** 验证集 Loss 下降说明模型更能压缩测试文本，但并不自动代表它擅长解决高中物理题或进行复杂代码生成

预训练阶段真正困难的问题：**如何把语言建模损失与任务能力之间的关系说清楚，而不是默认它们天然一致**。[**Paloma**](https://arxiv.org/abs/2312.10523) 这类工作之所以重要，就在于它明确反对 **单一 held-out perplexity 足以代表整体能力** 的简单假设

# 2. 内在评估：交叉熵、困惑度与分布拟合质量

预训练最基础的内在指标是 **负对数似然 (NLL)** 或 **交叉熵 (Cross-Entropy)**。给定验证集序列 $x_{1:T}$，其平均 Token 级损失为：

$\mathcal{L}_{\mathrm{NLL}} = -\frac{1}{T}\sum_{t=1}^{T}\log p_\theta(x_t \mid x_{<t})$

取自然指数后，即为 **困惑度 (Perplexity, PPL)**：

$\mathrm{PPL} = \exp(\mathcal{L}_{\mathrm{NLL}})$

> 困惑度的直观含义是：**在预测下一个 Token 时，模型平均面临多少个看起来同样可能的候选选项**。PPL 越小，说明模型在预测时越笃定（分支越少）。如果 **PPL 为 10，就意味着模型在预测下一个词时，平均要在 10 个选项中艰难猜测**。因此它仍然是预训练评估中最直接、最基础、也最难被完全替代的指。[Kaplan](https://arxiv.org/abs/2001.08361) 等人的研究之所以能够建立缩放律，本质上就是因为 cross-entropy loss 在大尺度下具有相当稳定的统计行为

## 代码实战：计算语言模型的 Perplexity

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

model_name = "gpt2"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name)
model.eval()

text = "The quick brown fox jumps over the lazy dog."
inputs = tokenizer(text, return_tensors="pt")

with torch.no_grad():
    outputs = model(**inputs, labels=inputs["input_ids"])
    nll = outputs.loss.item()
    ppl = torch.exp(outputs.loss).item()

print(f"NLL (avg token loss): {nll:.4f}")
print(f"Perplexity: {ppl:.2f}")
```

## 跨词表比较的陷阱：BPB (Bits-Per-Byte)

* 但是困惑度并不是一个完全可比的绝对量，PPL 显著依赖于 **Tokenization、文本清洗规则、序列切分方式** 等策略。相同语料在不同 BPE 词表下的 Token 数不同，当你 **比较不同生态的模型时，直接对比 Token-level PPL 可能会将词表压缩率差异误判为模型质量差异**
  更稳妥的做法是采用 **字节级归一化指标 (Bits-per-byte, BPB)**：
  $\mathrm{BPB} = -\frac{1}{B}\sum_{i=1}^{B}\log_2 p_\theta(b_i \mid b_{<i})$
  其中 $b_i$ 表示第 (i) 个字节，(B) 为总字节数。BPB 的优势在于 **归一化单位更加稳定，更适合跨 tokenizer 或 byte-level / subword-level 模型比较**
  > 近年的 byte-level 模型研究和数据选择研究都倾向于在跨模型族比较时引入 BPB，而不是仅用 token-level PPL，https://arxiv.org/html/2404.14408v3
* **领域分解也** 至关重要。单一验证集上的 PPL 往往是不充分的。例如，数据清洗可能会提升代码或百科语料的拟合质量，但同时导致某些长尾学科知识的 PPL 恶化。因此，报告 **分领域困惑度剖面** 比提供单个总 PPL 更有解释力
* **评测协议** 本身也会影响结论。[Catwalk](https://arxiv.org/html/2312.10253v1) 与 [OLMo](https://arxiv.org/abs/2402.00838) 相关工作强调，进行困惑度评测时应 **避免粗糙的文档拼接和不规范的窗口切分，因为这会改变上下文边界条件，进而扭曲 loss 估计**。对于长文本，通常需要采用非重叠或滑动窗口推断，并明确说明上下文截断方式、padding 策略和是否跨文档共享上下文

# 3. 从缩放律看预训练评估：比较前沿位置

预训练模型评估若脱离 Scaling Laws 的视角，常会犯一个很基本的错误：**把某个 Checkpoint 的单点性能，当作体系设计优劣的充分证据。** 语言建模损失可近似表示为参数量 $N$ 和数据量 $D$ 的幂律函数：

$L(N,D) \approx L_\infty + aN^{-\alpha} + bD^{-\beta}$

其中 $L_\infty$ 表示不可约损失，$\alpha,\beta$ 为经验指数，它说明更大模型、更大数据、更大算力与损失改善之间具有规律性的边际收益递减关系。[**Chinchilla**](https://arxiv.org/abs/2203.15556) 的贡献是把怎么评估预训练方案是否高效进一步形式化。该工作在固定训练计算预算下比较不同参数量和训练 token 数的配置，发现很多大模型实际上处于 **参数过大、训练不足** 的状态，并提出 **在 compute-optimal 前沿上，模型规模和训练 token 数应近似同步扩展**

对评估而言，这意味着不应只报告70B 模型优于 13B 模型，而应同时回答：**它是否只是因为看了更多 token？是否处在更优的计算分配点上？是否在同等 FLOPs 条件下仍然占优？**

严谨的预训练报告不应只是数字的罗列，而应呈现以下曲线：

1. **收敛曲线：** 验证损失 vs. Token 数，观察优化是否充分
2. **前沿曲线：** Loss vs. 总训练 FLOPs，比较方法效率
3. **能力映射曲线：** 外在 Benchmark 分数 vs. 内在 Loss，判断拟合收益是否成功转化为任务能力

# 4. 外在评估：核心能力基准演进

**仅靠 PPL 无法说明模型在知识、常识、数学推理、复杂代码编写和多学科问答上是否真正具备可迁移能力**，因此预训练评估必须引入外在基准。引入外在评估必须坚持 **预训练态** 原则：**优先使用标准化的 Zero-shot/Few-shot 协议，避免复杂的 CoT 模板或外部工具增强带来混淆，** 下表总结了当前预训练评估的核心基准及其演进趋势：



| **评估维度** | **经典基准代表** | **核心指标公式 / 解释** | **当前局限与演进方向** |
| --- | --- | --- | --- |
| **百科与学科知识** | **MMLU** | $\mathrm{Acc} = \frac{1}{N}\sum_{i=1}^{N}\mathbf{1}[\hat y_i=y_i]$ | 偏向知识回忆；演进至 **MMLU-Pro** (扩大至10选项，增加推理负载，移除噪声与过易题目，更高的 prompt 稳定性) |
| **科学与常识推理** | **ARC / HellaSwag** | 选项对数概率对比 | 容易被模型利用选项风格伪迹作弊，仅能作为局部切片参考 |
| **数学推导** | **GSM8K** | Exact Match (EM 基于最终答案) | 题库严重污染；正向更难的 **BBEH** 或过程监督 (PRM) 演进 |
| **代码生成** | **HumanEval** | $\mathrm{pass@}k = 1-\frac{\binom{n-c}{k}}{\binom{n}{k}}$ | 静态题库易泄露；正向持续更新的 **LiveCodeBench**演进 |
| **中文及本土化** | **C-Eval / CMMLU** | 准确率 (Acc) | 必须考虑本地化语境，英文分数无法直接外推到中文场景 |



* 在 **知识与学科理解** 方面，**MMLU** 仍然是预训练评估中最有影响力的基准之一。它覆盖 57 个学科，采用多项选择题形式。MMLU 的价值在于 **学科跨度大，能够粗略测量模型的学术型知识广度**；但它的局限也很明显，即题 **目中相当一部分更偏知识回忆而非深层推理，并且对 prompt 格式、选项扰动和污染都较为敏感**
  ```python
  # MMLU 评测的核心是构造标准化 few-shot prompt
  MMLU_TEMPLATE = """The following are multiple choice questions about {subject}.

  {few_shot_examples}
  Question: {question}
  A. {A}
  B. {B}
  C. {C}
  D. {D}
  Answer:"""
  import torch
  def eval_mmlu_item(model, tokenizer, prompt, choices="ABCD"):
      """返回模型认为最可能的选项"""
      inputs = tokenizer(prompt, return_tensors="pt")
      with torch.no_grad():
          logits = model(**inputs).logits[0, -1, :]  # 最后一个位置的 logits
      choice_ids = [tokenizer.encode(c, add_special_tokens=False)[0] for c in choices]
      choice_logits = logits[choice_ids]
      return choices[choice_logits.argmax().item()]
  ```
* 在 **数学推理** 方面，**GSM8K** 仍然是基础但极具代表性的基准。它由 **8.5K 高质量小学到初中级别数学应用题** 组成，强调 **多步推理和中间变量处理**。GSM8K 的价值在很早就把知识问答与过程推理区分开来。在以预训练为对象的评测中，GSM8K 更适合作为基础算术与短链推理探针，而不应被过度外推为一般性数学能力的总代表
* 在 **代码能力** 方面，**HumanEval** 与 **MBPP** 是最经典的两类基准。HumanEval 强调从 docstring 到函数实现的程序综合，MBPP 则更偏入门级 Python 题。代码生成和一般文本生成不同，它通常采用可执行的函数正确性标准，而非字符串重叠。HumanEval 采用的核心指标是 **pass@k**。若对 **每个问题采样 n 个程序，其中 c 个能通过单元测试**，则 $\mathrm{pass@}k = 1-\frac{\binom{n-c}{k}}{\binom{n}{k}}$。这个指标衡量的是在 **最多尝试 k 个候选时**，**至少找到一个正确程序的概率**，比单次 exact match 更符合程序综合任务的本质。（形象一些： <u>共有 </u>**<u>n</u>**<u>个候选代码，其中 </u>**<u>c</u>**<u> 个是正确的。你随机从中抽取 </u>**<u>k</u>**<u> 个来看，</u>**<u>只要这 k 个里面包含至少 1 个正确的代码</u>**<u>，我们就认为模型在这道题上 Pass（及格）了</u>）
* 对于 **中文** 预训练模型，仅使用英文 benchmark 明显不足。C-Eval 与 CMMLU 已成为较有代表性的中文知识与学科评估集。C-Eval 覆盖中学、大学和职业层面的 52 个学科，并提供更难的 C-Eval Hard；CMMLU 同样从自然科学、社会科学、工程和人文学科多个方向测量中文环境下的大模型能力
* 随着旧 benchmark 饱和，仅依赖 **MMLU、BBH、HumanEval** 这类经典集合已经越来越难区分强模型。因此，预训练评估正在向更高难度和更低污染方向演化。**MMLU-Pro** 通过提高题目质量和选项数缓解了原始 MMLU 的天花板效应；**BBEH** 作为 BIG-Bench Hard 的进一步升级版，针对更广义的推理技能重新构造更难任务；**LiveBench** 则通过持续引入新题和强调客观判分来降低静态公开题库带来的泄漏风险

# 5. 可信度评估：校准与置信度

评估预训练模型不能只看答对率、准确率，还要看 **模型是否知道自己不懂**。MMLU 原始论文就指出，大模型在若干重要学科上不仅 **准确率有限**，而且 **经常不能正确识别自身错误**。对选择题或标签空间明确的任务，可以进一步研究模型输出概率的校准性。这可以通过 **期望校准误差 (Expected Calibration Error, ECE)** 来衡量：

$\mathrm{ECE} = \sum_{m=1}^{M}\frac{|B_m|}{N} \left| \mathrm{acc}(B_m)-\mathrm{conf}(B_m) \right|$

其中 $B_m$ 表示第 m 个置信度区间中的样本集合，$\mathrm{acc}(B_m$) 和 $\mathrm{conf}(B_m$) 分别是该区间的经验准确率与平均置信度。如果模型的 80% 置信回答大约也有 80% 的正确率，则它具有良好的校准性

* **高准确率但过度自信** 的 Base Model，在后续 SFT 阶段容易表现出一本正经地胡说八道
* **准确率略低但校准极好** 的模型，在检索增强 (RAG) 和拒答机制中往往更具可塑性

因此，预训练报告若只报平均 accuracy 而不报 calibration、per-category breakdown 和 uncertainty behavior，其实遗漏了对模型认知结构的重要信息

# 6. 数据污染：预训练评估最棘手的问题

如果 benchmark 题目本身，或者其近似改写、翻译版本、解析答案，已经出现在预训练语料中，那么高分究竟来自泛化，还是来自记忆？这一问题在数学、代码和考试型基准中尤为严重。可以利用 **perplexity 与 n-gram accuracy 识别泄漏风险**，如果只做 **精确的字符串匹配去重 (Exact Match Decontamination) 远远不够**，因为翻译、改写足以绕过规则

这类污染问题对预训练评估的破坏是结构性的。首先，它会 **夸大模型在特定 benchmark 上的能力**，导致不同模型间比较失真。其次，它会扭曲研究方向，因为研究者可能误以为 **某种架构、数据配方或训练技巧带来了泛化提升，实际上只是更高效地记住了公开题库**。再次，它会让 **静态 benchmark 逐渐失去边际信息价值**，因为模型越强、抓取网页越广、题库传播越充分，公开测试集就越难继续扮演未见分布角色

**严谨的污染控制策略：**

1. 明确公开训练数据来源和去污染机制
2. 引入 **时间滞后的新鲜基准**（如 LiveBench 等持续更新集）
3. 执行基于语义的去污染 (Paraphrase-aware Decontamination)

# 7. 实践指南：如何执行预训练阶段评估？

对于学习者而言，预训练评估绝不是铺满十几个 Benchmark 跑分，而是要建立一个 **最小可解释闭环**。建议遵循以下 5 步：

1. **分域构建验证集：** 按代码、学术文本、垂类数据（如物理/化学题库）切分独立验证集
2. **执行内在评估：** 固定切分窗口和上下文长度，严格计算各领域的 NLL / PPL。若存在词表差异，务必计算 BPB

| Domain | NLL | PPL | BPB |
| ------ | --- | --- | --- |
| 通用网页 | — | — | — |
| 学术文本 | — | — | — |
| 代码 | — | — | — |
| 百科/问答 | — | — | — |

* **构建最小外在面板：** 每个核心能力选取 *一个* 代表性基准（如：知识选 MMLU，代码选 HumanEval）。先画出四象限能力图，按需扩充
* **严格执行污染检查：** 交叉比对高分 Benchmark 样本与训练集的相似度，补测新鲜数据集以挤出记忆水分
* **建立因果映射：** 最终报告的结构应是：*“我们在 X 领域的语言建模损失下降了 Y%，这主要映射到了 Z 能力上的提升，且校准度 (ECE) 保持稳定”*

只有当评估框架能反过来指导数据配比、架构选择和预算分配时，它才真正具备工程与科学双重价值。

> 预训练阶段的评估，本质上是在回答三个逐层递进的问题：
> * 第一，模型是否更好地拟合了语言分布
> * 第二，这种拟合是否转化为了跨任务可迁移能力
> * 第三，我们观察到的能力提升究竟来自真实泛化，还是来自评测协议偏差与数据污染
> 相应地，严谨的预训练评估也必须由三部分构成：以内在损失和 BPB 为核心的 **分布拟合评估**，以 MMLU、ARC、HellaSwag、GSM8K、HumanEval、C-Eval 等为 **核心的能力迁移评估**，以及以校准、稳健性和去污染为核心的 **可信度评估**。离开这三部分中的任何一部分，所谓预训练效果更好的结论都不够扎实
